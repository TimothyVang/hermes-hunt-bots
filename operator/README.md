# Operator tools

These scripts run the six-bot hunts and the watcher improvement loop against the local lab. They are for the person operating the lab, not for the bots. Several of them read the operator-only answer keys, so nothing here is ever wired into a bot prompt, profile, or tool.

Every path derives from this clone's root and its git-ignored `runtime/` folder. Environment variables override the defaults. `lab_paths.py` defines all of them, and the scripts share it.

## Tools

| Tool | What it does | Needs |
|---|---|---|
| `switch_case.py` | Stops the lab VM, reseeds it with another case (fresh seed per load), starts it once available memory covers the deployment plus headroom, and waits for the lab health API to report the new seed's cloud-init instance (the previous boot's lab server answers first, for the old guest software). With no case it only starts the VM. `--hold` keeps the process (and the VM it owns) alive. | Hermes, prepared lab VM |
| `tool_loops.py` | The watcher improvement loop. Runs the hunt for 2 rounds, scores the final reports against the answer key, and asks a watcher model (Claude Opus through the lab home's `default` Hermes profile, no tools) for one general change to the brief or per-stage guidance. A change is kept only if the mean score rises by at least one fact without adding halts. Stops on perfect, after `--loops`, or after 3 loops without a kept change. Each round's record lists its handoff rejections (step, outcome, validator reason), and `result.json` counts the workflow's handoff retries. A round's `usage` sums every billed attempt, including each retried attempt that survives only as its handoff rejection's result; `steps_without_usage` counts attempts without usage and `retried_attempts` the retried ones. | Hermes, running lab, Temporal worker, answer key |
| `auto_run.py` | Starts the VM whenever memory allows, waits for the health API, then runs `tool_loops.py` as a child with the same arguments and holds the VM afterwards. Run it as a long-lived service. | Same as `tool_loops.py` |
| `film_loop.py` | The filmed full-mode loop. Each loop runs one round in which the Threat Hunter drives Kibana Discover (Elastic) and the Network Analyst drives Arkime through `lab_browser`, films the round's Hunt Live board, scores it, measures driving coverage, cuts a 1x master and a constant-speed video, and has Claude Opus review the constant-speed video. The watcher then proposes the next brief, stage guidance and drive note. A change is kept only with 0 decoys blamed, no halt, and either more coverage at the same or better score or a better score with coverage at most 0.1 lower, or a coverage gain of at least 0.2 with the score at most 2 lower (one round per loop scores within about 2 of noise). `--resume --rejudge-last REASON` re-applies the current rule to the last loop if it was reverted and logs REASON. `--resume --reset-plateau REASON` zeroes the no-gain counter after an infrastructure fix and logs REASON. Every lane's Hermes home needs a persistent gateway started the normal way (`HERMES_HOME=<home> hermes gateway run`): the bots' tools and browsers run inside it, and one a worker auto-starts inherits the worker's stripped environment and exits when idle (lab_browser failed most calls under it). `film_loop.py` refuses to start without one. A new series can start from an earlier series' best with `--seed path\to\BEST.json` (a film-loop or tool-loop one). Stops when the best loop finds 18/18 with coverage >= 0.8 and a review that says ready, after `--loops`, or after 3 loops without a kept change. | Hermes, running lab, Temporal worker, answer key, ffmpeg, the `lab_browser` demo marker, Chromium or Edge |
| `film/record.py` | Films one round on one lane from its Hunt Live board, never the desktop. It starts the lane's own board (`python -m hermes_temporal.board` with the round's `--workflow-id` and `--input`, the lane's `--lab-state-dir` and `--hermes-home`) on a free loopback port, opens it in a dedicated headless Chromium/Edge with its own temporary profile and a 1920x1080 page at device scale 1, and saves its `Page.startScreencast` frames with their timestamps (`board/`, `board-index.jsonl`). It samples the board's step states every second (`board-state.jsonl`), screencasts the lane's bots' browsers, and runs the round through `tool_loops.run_config` on the lane's lab and task queue. Browser and board stop when the round ends. Writes `film.json` (`t0`, `board_port`, `board_frames`, `board_state_samples`, `screencast_frames`). | Python `websockets`, Chromium or Edge |
| `film/screencast.py` | Saves each browser owner's `lab_browser` browser as screencast frames. The watch-only DevTools client itself lives in `framework/hunt_lab/screencast.py`, shared with the Hunt Board's live browsers: it attaches as soon as Chromium writes `hunt-lab-browser/<profile>/user-data/DevToolsActivePort`, so the first search typed into a fresh browser is filmed, then follows the main target that `session.json` names, and re-attaches when a new browser launches or the main target changes. It can send only target listing, attach, detach, screencast start/stop and frame acks. This module writes every `Page.startScreencast` frame with its timestamp and an `index.jsonl`. | Python `websockets` |
| `film/edit.py` | Cuts the board frames into `video-full.mp4` (Option A: the whole round at 1x) and `video.mp4` (Option B: the whole round at one constant `speed`, default 5x, the cut the loop reviews). Each frame is held until the next. A bottom bar carries a permanent label ("5x speed · every frame is real") and, with `captions`, the bot and tool acting. A chapter card opens each wave at its first step's real start, as the board showed it: "Wave n of N" with its step names (a serial round has one step per wave), owner bots, wall-clock range, duration, and its dropped or stopped steps grouped by state and reason. A dropped step counts as ended. Lines are wrapped to 1920 px and capped at 14 per card, the cut lines counted on the last. Intro and outro cards carry the round's real numbers; the outro also counts steps done, dropped, stopped and not reached, and waves, from the board's last state. Writes `edit.json` with the segments, per-step timings and both cuts' timelines. `cut(..., out_dir=...)` re-cuts an earlier loop's captures without overwriting its first cut. | ffmpeg |
| `film/review.py` | Stacks a browser-moment contact sheet (the bots' own screencast frames at their browser actions) and an overview of the reviewed cut into one image. It sends that image with measured metrics (board seconds, chapters, longest frozen board, browser-on-screen seconds, captions) to Opus (one call, one retry on invalid JSON) and validates the reply: tools driven, typing and cursor visible, readability, dead time, brief suggestions, and knob changes from a fixed set (`speed`, `captions`, `intro_title`). | Hermes, ffmpeg |
| `film/lanes.py` | Reads a `--lanes` file for `film_loop.py` and refuses lanes that could interfere: shared name, Hermes home, browser state or task queue. | none |
| `drive_gates.py` | Drives the execute and review gates of one practice run in one of two opt-in modes; exactly one must be chosen. `--two-decisions --operator "<name>"` leaves the operator's two decisions per hunt (HUNT-BOTS.md rule 3) to the operator: at the review of the `scope` step (a parallel hunt's `wave-<n>` review while `scope` awaits review) and at the review of the hunt's last step (`incident`; in a parallel hunt the highest wave) it sends nothing, saves the outputs, logs `WAITING FOR OPERATOR <name>: <scope|report> review of <child> <gate>; outputs in <dir>` once, prints the `hermes_temporal.cli decision` command to approve or deny, and polls until the operator decides or the workflow ends. Every other gate is approved automatically with a note that names it an automated approval for that operator and not a human review of the step. `--delegated-by` and `--reason` instead approve every gate on that person's behalf. In both modes it saves each stage output and stops on the first non-completed outcome of a required step, including an operator's denial. It never retries on its own. When the workflow re-offers a step once after handoff validation rejected its output, the driver approves that new execute gate under its own decision ID, with a note that names it a retry approval, and saves the corrected output. A parallel hunt gates a whole wave at once (gate ID `wave-<n>`): the driver sends one execute approval each time the wave's execute gate opens (once, and once more for the steps being retried) and one review approval, after saving the output of every step awaiting review under that step's own ID, matched to results by execution ID. It never approves a wave it could not save in full. An optional step the workflow dropped is logged as `DROPPED` and the run goes on. **Decision log:** every decision it sends is appended to `decisions.jsonl` in `--decision-dir` (default `runtime/practice/operator-decisions/`) as one JSON line, written with a single append and never rewritten: UTC `ts`, `workflow`, `child`, `gate`, `phase`, `choice`, `decided_by` (`automated` or `delegated: <name>`), `channel` (`drive_gates`), `decision_id` and the note's `note_sha256`. Each decision it sends also carries `--decided-by <operator or delegating person> --via automated`, which the workflow records with the gate (`status` field `decisions`). **Pending records:** in two-decision mode, when it starts waiting at the operator's gate it writes `pending/<child>__<gate>__<digest>__review.json` atomically (the IDs with unsafe characters replaced, plus 16 hex of the SHA-256 of the exact child and gate, so IDs that sanitize alike never share or delete each other's record): child, workflow, gate, `kind` (`scope` or `report`), a one-time `nonce`, `opened_at`, `outputs_dir` and `decision_cli` (the decision command without choice, ID or note). `--card-summary` adds `summary`: the scope step's output, or the report's verdict (its disposition) and first three claim statements, without control characters, prefixed `Bot-written, unverified:` and capped at 2,500 characters. When the gate moves on it deletes the record and reads the workflow's own record of that review decision. Unless `decisions.jsonl` already holds that decision ID, it appends a line with the recorded choice and decision ID, `channel` `workflow_record`, `via` and (when recorded) `slack_user` as the workflow holds them, and `decided_by` `stated: <name>` (`operator (outside driver)` when the decision carried no identity): the workflow does not authenticate the sender, so these lines are never labelled like the bridge's checked `human:` / `slack` lines. If the bridge had logged a different decision that the workflow ignored, the driver log says so. For a workflow that records no deciders (one that took its first gate decision before running patch `gate-decider-v1`) it keeps the earlier rule: unless `slack_gates.py` logged that decision, it appends a line with `decided_by` `operator (outside driver)`, `channel` `unknown` and the outcome the workflow shows. A gate that timed out is logged as closed, not as a decision. The printed decision commands carry `--decided-by <operator>`. See Safety. | Temporal worker |
| `slack_gates.py` | The operator's opt-in Slack bridge (ADR 0004), a long-running service. It posts one card per pending record of `drive_gates.py --two-decisions` to `--channel` (or a DM with the first `--operator-user`) over Slack Socket Mode, which connects outbound only, and remembers each card in `posted/` so a restart posts nothing twice. A card shows the workflow, hunt run, gate, kind, opened time and outputs folder; `--content summary` adds the record's summary in a quote labelled bot-written. Approve / Reject (Accept report / Reject report) from a Slack user ID on `--operator-user` opens a form that asks "What did you check?" (required, at most 1,000 characters). On submission it re-checks the user, the record and its nonce, claims the record (`pending/` to `claimed/`, so a gate is decided once), confirms with `status` that the gate is still open, and sends one `hermes_temporal.cli decision` on loopback with the ID `<child>:<gate>:review:<nonce>` and the note `Decided by <name> (Slack user <id>) via Slack at <UTC>; card <nonce>. Checked: <your text>` (capped at the workflow's 4,096 bytes), plus `--decided-by <name> --via slack --slack-user <id>`, which the workflow records with the gate. It then appends a `decided_by` `human: <name>`, `channel` `slack` line with `slack_user` to `decisions.jsonl` and updates the card to say who decided what and when. Anyone else, a stale or replaced card, or a gate already claimed is refused; a failed send puts the record back and shows only an error code. It runs only the hermes_temporal.cli decision a record names for its own gate, with its own Python and a loopback address at most. Log lines carry the workflow, gate, Slack user ID and outcome only. See Slack bridge and Safety. | `slack-sdk==3.45.0`, a Slack app, Temporal worker |
| `diagnose_rejections.py` | Replays handoff validation for halted loop rounds and prints the exact rejection reason. A parallel hunt's results are matched to steps by execution ID. Read-only. | Temporal, the framework's Python dependencies in the running interpreter |
| `work_hunt.py` | A work hunt in one command (see "Loading a work export" in [framework/README.md](../framework/README.md)). Prints a reminder that only unclassified, non-CUI work data may be exported, refuses a `--case-id` whose case, export or work folder exists, then: exports `[--start, --end)` of `--index` from `--url` with `hunt_lab.import_elastic export` (the key only from `HUNT_ELASTIC_API_KEY`, which it removes from its own environment and gives to the export child alone; an empty window stops here), imports it into `runtime/cases/<case>/evidence`, loads it with a `switch_case.py --hold` holder in its own process group that keeps the lab loaded after the command ends (`--reseed-python` names a Python with pycdlib), exports the hunt input with `lab-input --tool-driven --data-origin work-export`, starts one parallel round with `--follow-ups` follow-up hunters (default 6) and runs `drive_gates.py` in the foreground. `--operator "<name>"` is two-decision mode: you approve the scope and decide the final report with the printed command or the Slack bridge (minimal cards); every other gate is recorded as automated. `--delegated-by` and `--reason` approve every gate on that person's behalf, recorded as delegated. Prints the export and import summaries, the lab's READY line, the workflow, its outcome, tokens and final report path, how to resume a failed gate driver, and how to stop the holder and the VM (`hunt-lab stop`; the VM runs detached from the holder), and writes `runtime/practice/work-hunts/<case>/hunt.json` with who decides the gates. A run that ends early once the holder is up (a failed step, Ctrl+C, an error) still writes that record with `ended_early` and prints the stop commands, plus the gate driver's resume command once the workflow exists. An export or import that runs past 60 minutes or is interrupted with Ctrl+C is killed, waited for, and its partial output removed (the export file, or the whole new case folder); a path it cannot remove is named so you can delete it. Nothing is scored: work data has no answer key. | Hermes, prepared lab VM, Temporal and a worker, a read-only Elastic API key |
| `team_probe.py` | Measures a team of Threat Hunters on the loaded case without Temporal. `concurrency` runs the scope step, then `--hunters` copies of the hunter at the same time on one Hermes home, and reports how many returned a valid handoff, each one's seconds and tokens, and the failure reason codes. `compare` runs paired arms per round on one shared scope output: `baseline` (one hunter), `split` (`--hunters` hunters, each with one fixed, case-agnostic assignment such as persistence or exfiltration) and `followup` (one hunter, then one follow-up hunter per finding that pivots to complete its evidence). Each arm's valid handoffs are merged and scored at the hunter stage only: attack facts fully and partly evidenced and decoys blamed. A hunter without a valid handoff contributes nothing, as the parallel workflow would drop it. Every session is launched as the worker launches a step, with usage recording. `--max-hunter-runs` is required and is a hard cap on native sessions; the command refuses to start if its plan exceeds it. Writes `rounds.json` and `summary.json` under `--out` and a line per arm to `practice/team-probe/probe.log`. It launches live model sessions and costs money. | Hermes, running lab, answer key, the framework's Python dependencies |
| `review_reports.py` | Q2 scores check; calls no model. `check`: for every round in `--rounds`, cited event IDs that do not exist (G2.1); whether each claim's named hosts, users, processes, IPs and domains appear in the events it cites (a subdomain counts for its domain); whether each answer-key fact's events exist and contain its entities (G2.2); and the scorer's found / partial / missed per fact, into `checks.json`. `packets`: per case, a claims packet without the answer key and a facts packet, each with the fixed reply schema, for an independent reviewer model. `agree`: validates the reviewer's replies (G2.3), run 1 vs run 2 claim agreement (G2.4) and scorer vs reviewer per fact with every disagreement listed (G2.5), into `agreement.json`. Reads answer keys; writes to `runtime/practice/review/q2/`. | Runtime case folders, answer keys and saved gate outputs |
| `check_keys.py` | Model check of an answer key; never changes a key. For each attack fact of `--case` (the first `--facts N` only, one model call each) it writes a packet with the fact's observation, every evidence group's accepted event records (at most 20 per group) and the case's other events of the processes those events belong to (same `process.entity_id`, or `winlog.event_data.ProcessGuid` for a Sysmon record with no `process` field such as DEDALE's unparsed file deletions; at most 60, excluding every attack fact's key events), and asks a reviewer model through `omp -p` whether each group's accepted events prove that part of the step: `proves`, `partly` or `does_not_prove`, with a reason and any listed process events that would prove it better. omp runs from a scratch folder holding only the packet and a settings overlay, with no session, skills, rules, context files or extensions, and with no tools: `--no-tools` leaves MCP servers connected, so the overlay (`--config`) adds every omp discovery provider to the user's own `disabledProviders` (checked live: the reviewer then reports no callable tool). `cursor` stays enabled only when the reviewer model is a `cursor/` model, since that id also names a model provider. `--model` picks the model; without it the report records omp's default model role, or `unknown`. Replies are validated against the packet's schema; an invalid reply is listed under `failures`, never as a verdict. Writes `keys-<case>.json` (every verdict, and under `disputed` each group not judged `proves`) beside the packets and raw replies in `--out` (default `runtime/practice/review/keys`), after removing that case's packets, replies and report from an earlier run; `--packets-only` calls no model and writes no report. Reads answer keys. | omp signed in to the operator's subscription |
| `cost_arms.py` | Q4 cost check; calls no model. Takes one rounds file per arm (`--arm K0=k0.jsonl --arm K3=k3.jsonl --arm K6=k6.jsonl`) and writes `runtime/practice/cost/q4/summary.json` plus a short table. G4.1: every `--cases` case (default `team-med-011`–`015`) has one completed hunt in every arm, with usage for every step; missing, halted and unmetered hunts are listed. G4.2: on the cases present in every arm (the others are listed and left out), the chosen arm has the lowest mean tokens per hunt among arms within one mean attack fact of `--baseline` (default `K6`), with 0 halts and no more decoys blamed in total; otherwise "none qualifies". G4.3: the cost of one hunt per arm by token type (uncached input, cache read, cache write, output; Hermes counts cache reads and writes inside `input_tokens`) at the `--prices` table, with its source. `prices.example.json` shows the table's shape; its rates stay null until the operator fills in Anthropic's current list prices (the cache-write rate for the cache lifetime the lab uses). Rounds files have no per-model split, so every token is priced at the table's one model. Rounds files written before usage counted retried handoff attempts (their usage has no `retried_attempts`) undercount any retried step; run `recount_usage.py` on them first. | The runner's rounds files, a price table |
| `recount_usage.py` | Recounts a rounds file's usage; calls no model. For each hunt it queries its round's child workflow status (`<workflow>:round:<round, default 001>`) through `hermes_temporal.cli status`, recomputes the usage with every retried handoff attempt included, prints the old and new `total_tokens`, and writes `<name>.recounted.jsonl` next to the input, which it never changes. A hunt whose status cannot be read or records no usage loses its usage in the copy (with `usage_recount_error`) so `cost_arms.py` lists it as unmetered, and the exit code is 1. | Temporal with the rounds' workflows |
| `toolcam/toolcam.mjs` | Follows the lab's `/activity` log during a live hunt and shows each bot's tool call as it happens (Arkime calls in Arkime's UI, other calls as the exact query and the rows the lab returned). Captures timestamped 1920x1080 frames twice a second. Reads hunt progress from the Hunt Board on `127.0.0.1`; `toolcam/progress.mjs` turns it into the status line (the open steps of the current wave, counted by state past four, steps done, dropped and stopped steps with their reason) and the closing card: "Hunt complete", or "Hunt ended early" with the waves never reached. | Bun, Edge or Chromium, running lab and board |
| `toolcam/assemble.py` | Turns tool-cam frames into a 1080p video. Each tool call plays at real speed for 2.5 s; time when the bots are only thinking plays 20x faster under a visible "20x speed" badge. Frames are never reordered or invented. `--end-card` appends a still for `--end-seconds`. | ffmpeg |
| `toolcam/card.mjs` | Renders a 1920x1080 HTML card to PNG for `--end-card`. | Bun, Edge or Chromium |

Every Python tool answers `--help` without the lab running. When a tool needs Hermes and `LAB_HERMES_EXE` is unset, it stops with a message naming the variable. It also stops, naming the file, while the lab home holds `.hermes-update-in-progress` (a Hermes update is running there, or a stale marker says which process left it).

The film loop's tests use no lab, browser, Temporal or ffmpeg. Run them from the repository root with `python -m unittest discover -s operator -p "test_*.py"`. `scripts/hunt_bots_check.py` runs every operator test as `operator tests:`.

## Examples

PowerShell, from the repository root, with a case generated as in [GETTING-STARTED.md](../GETTING-STARTED.md):

```powershell
$env:LAB_HERMES_EXE = '<path to the lab home hermes.exe>'
$env:HUNT_BOTS_PYTHON = "$PWD\.venv-dev\Scripts\python.exe"
$env:HUNT_BOTS_TEMPORAL_ADDRESS = '127.0.0.1:7233'
$env:HUNT_BOTS_TASK_QUEUE = 'hermes-temporal'

# Load a case and keep the VM alive (run as a long-lived service)
python operator\switch_case.py runtime\cases\lab-med-001\evidence --hold

# Approve the gates of one practice run you started yourself
python operator\drive_gates.py my-first-hunt --delegated-by "Ada Lovelace" --reason "approve every gate of this synthetic practice run"

# Watcher loop on the loaded case
python operator\tool_loops.py lab-med-001 runtime\operator-only\lab-med-001\truth.json --delegated-by "Ada Lovelace" --reason "unattended synthetic watcher loop" --loops 8 --tag -a

# Filmed full-mode loop (needs the demo marker, see below); FFMPEG must point at ffmpeg.exe
$env:FFMPEG = "$PWD\..\runtime\tools\ffmpeg\bin\ffmpeg.exe"
python operator\film_loop.py lab-med-001 runtime\operator-only\lab-med-001\truth.json --delegated-by "Ada Lovelace" --reason "unattended synthetic film loop" --loops 8 --tag=-f1

# Same, but start the VM first whenever memory allows
python -u operator\auto_run.py lab-med-001 runtime\operator-only\lab-med-001\truth.json --delegated-by "Ada Lovelace" --reason "unattended synthetic watcher loop"

# Resume after an infrastructure fix without counting the broken loops against the plateau
python operator\tool_loops.py lab-med-001 runtime\operator-only\lab-med-001\truth.json --delegated-by "Ada Lovelace" --reason "unattended synthetic watcher loop" --resume --tag -b --reset-plateau "worker restarted"

# Why did loop 3 halt?
python operator\diagnose_rejections.py runtime\practice\tool-loops\loop-03=loop-03-lab-med-001:round:001

# Record a hunt and cut the video
bun operator\toolcam\toolcam.mjs runtime\practice\cam <lab_url> <arkime_url> lab-med-001 <startEpoch> <stopEpoch> <activityAfter>
bun operator\toolcam\card.mjs runtime\practice\end.html runtime\practice\end.png
python operator\toolcam\assemble.py runtime\practice\cam runtime\practice\hunt.mp4 --end-card runtime\practice\end.png
```

`--tag` suffixes every workflow ID so a restarted series never reuses one.

`film_loop.py` needs the operator's demo marker `hunt-lab-browser\demo.json` (for example `{"headed": true, "window": [0, 0, 1280, 1080], "cursor": true}`) under the `framework-network-analyst` profile of the lab home. Without it the bots do not type searches on screen and `film/record.py` refuses to start. `HUNT_BOTS_PYTHON` must have `temporalio` and `websockets`, since it runs the board. Loop state goes to `runtime/practice/film-loops/`: `state.json`, `BEST.json`, `BEST.mp4`, `loop.log`, and one `film-NN` directory per loop holding the captures, `video.mp4`, `video-full.mp4`, `review.png`, `review.json` and `decision.json`.

**Parallel lanes.** `--lanes lanes.json` runs each loop's round on several independent labs at the same time and scores the loop on the mean over lanes (any halt or blamed decoy in any lane fails the keep rule). A lane is its own Hermes home with its own lab VM, demo marker and `lab_browser` state, its own Temporal worker on its own task queue, and its own Hunt Live board and headless browser for the film. The tools take the lane explicitly: Temporal calls use its queue, `hunt-lab status` runs against its home for the lab URL, and each lane's `drive_gates.py` runs with the lane's environment. Workflow IDs and folders carry the lane name (`film-03-f2-l2-lab-med-001`, `film-03/l2/`). The review sends one image with each lane's sheets stacked under its name. `BEST.mp4` is the kept loop's best lane's reviewed cut (a clean lane first, then most facts, then most coverage): a side-by-side would halve each lane. ## Slack bridge (opt-in)

The bridge is off unless you start it with your own Slack tokens. The bots get no messaging tool and take no part in it: the bridge is operator tooling that turns your answer into the same loopback decision the printed command sends. Setup, once:

1. At api.slack.com/apps choose **Create New App**, **From a manifest**, and paste `operator/slack-app-manifest.yaml`. It enables Socket Mode and interactivity, asks only for the bot scopes `chat:write` (cards, card updates, refusal notices) and `im:write` (opening the DM when `--channel` is not given), and subscribes to no events.
2. Under **Basic Information**, **App-Level Tokens**, generate a token with the `connections:write` scope. That is `SLACK_APP_TOKEN` (`xapp-...`). Check that **Socket Mode** is on.
3. **Install to Workspace**. **OAuth & Permissions** then shows the Bot User OAuth Token, `SLACK_BOT_TOKEN` (`xoxb-...`).
4. Find your Slack member ID: your profile, the more-actions menu, **Copy member ID** (`U...`). Only the IDs you pass to `--operator-user` can decide.
5. Install `slack-sdk==3.45.0` (the version upstream Hermes pins) into the Python that runs the bridge.
6. Turn on Slack two-factor authentication for your account: anyone who takes it over can approve.

Run, in the shell that starts the bridge only (tokens are typed, not kept in history, files or arguments):

```powershell
$env:SLACK_BOT_TOKEN = Read-Host -MaskInput 'Slack bot token (xoxb-)'
$env:SLACK_APP_TOKEN = Read-Host -MaskInput 'Slack app-level token (xapp-)'
python operator\slack_gates.py --operator-name "Ada Lovelace" --operator-user U0123ABCD

# In another shell, the gate driver writes the pending records the bridge turns into cards
python operator\drive_gates.py my-first-hunt --two-decisions --operator "Ada Lovelace"
```

Pass the same `--decision-dir` to both if you change it. The bridge polls `pending/` every 3 seconds. A restart is safe: posted cards are remembered in `posted/`, and a record left in `claimed/` by a bridge that stopped mid-decision is put back in `pending/` (its gate is checked again before anything is sent). The printed CLI command still works; a decision sent that way is logged by the driver as `operator (outside driver)`.

**Data boundary.** Slack (Salesforce) stores card text and your notes under the workspace's retention. Default cards (`--content minimal`) carry only the workflow and run IDs, the gate, the opened time and the local outputs path. Summary cards (`drive_gates.py --card-summary` with `slack_gates.py --content summary`) carry bot-written scope or report text and are for synthetic lab cases only; real or work data gets ID-and-status cards until a work boundary names Slack.

## Safety

- **Synthetic by default.** Point these tools at generated cases under `runtime/`. A real-data case (`"data_origin": "public-dataset"` or `"work-export"`, HUNT-BOTS.md rule 1; these loops do not run a `"work-connected"` case) is used only when the caller passes that same origin as `data_origin=` to `tool_loops.base_input`, or by `work_hunt.py`, which imports the work export itself and passes `--data-origin work-export` to `lab-input`; a cached input of any other origin is refused, and its scope keeps the origin label lab-input gave it and is never rewritten as synthetic. Their outputs (scores, reports, frames, videos) stay in `runtime/`, which Git ignores.
- **Answer keys stay with the operator.** `tool_loops.py` and `film_loop.py` read `runtime/operator-only/` to score reports and to reject case-specific words in the watcher's proposals. The watcher and the video reviewer see only fact categories and counts, never the key, and proposals must be general hunting technique. Nothing here feeds a key to a bot.
- **Automated approvals are labelled.** The operator makes two decisions per hunt: the scope approval and the acceptance or rejection of the final report (HUNT-BOTS.md rule 3). `drive_gates.py` refuses to run unless you choose exactly one mode. With `--two-decisions --operator "<name>"` it never decides those two review gates; you send them yourself, with the printed `hermes_temporal.cli decision` command or through the opt-in Slack bridge, and a note on what you checked. Every other approval it records says it is an automated approval under ADR 0002 for that operator, recorded by the script, and not a human review of the step. With `--delegated-by` and `--reason` it approves every gate, and every approval note says it is a delegated approval by that person, recorded by the script, and not a human review of the content. It prints its mode on start. `tool_loops.py`, `film_loop.py` and `auto_run.py` run it in delegated mode and require the same two flags because they run it for every hunt. Report runs driven in delegated mode as delegated, and runs in two-decision mode as automated apart from the operator's two decisions; never as human-reviewed throughout. `decisions.jsonl` names who decided each gate and through which channel.
- **Slack decisions are opt-in, one-shot and the operator's alone.** `slack_gates.py` runs only when you start it with your own tokens from the environment; it never writes, prints or logs them and strips every `SLACK_*` variable from the decision command it runs. Socket Mode opens no inbound port, and Temporal and the board stay on loopback. Only allowlisted Slack user IDs can answer, only for the record that is still pending with the card's nonce, only once (the claim rename), and only while `status` shows that gate open. The workflow records the identity the bridge sends with the gate (`--decided-by`, `--via slack`, `--slack-user`; `status` field `decisions`), and the bridge also writes it to the decision note and `decisions.jsonl`. Both records hold what the sender states; neither is authenticated. Anything that can write the decision folder can put a card in front of you; the bridge still runs nothing but the hermes_temporal.cli decision for the record's own gate, with its own Python and at most a loopback address. Card summaries are bot-written and unverified: read the outputs before deciding.
- **The tool cam only opens lab origins.** It reads the lab, Arkime, and the Hunt Board on `127.0.0.1`.
- **No desktop capture.** `film/record.py` films only the lane's own read-only Hunt Live board on `127.0.0.1`, in a headless browser with a temporary profile that is deleted afterwards, never the user's browser or screen. The bots' browsers are filmed through their own watch-only DevTools screencast. Do not use a desktop screenshot or capture anywhere.
- **Every frame is real.** The cuts use only board screencast frames and rendered cards. Each cut plays at one constant speed with that speed on screen throughout, and the cards show only measured numbers. The review may retitle the intro but never add digits.
