# Extension review and destination prerequisites

## Reviewed before local enablement

- **Candidate:** original `cybersecurity-workspace/plugin.js`, authored in this run. No community package, build artifact, binary, backend or remote script is imported.
- **Provenance:** source lives with the portable framework; plugin ID equals its directory. Imports are limited to the Hermes SDK and app-provided React JSX runtime. Its 16 px icons are Lucide 0.577.0 path data copied into the source with Lucide's ISC notice beside them (the SDK's own icon set is Tabler and lacks several of the approved icons). Review the exact source and its archive checksum before installation on another machine.
- **License:** the inspected Hermes checkout's root LICENSE is MIT, copyright Nous Research, with notice retention and warranty disclaimer. That root license is not a license grant for every dependency, video, catalog package or mascot. This run does not grant a new distribution license to the framework's original work. Local development only until the rights holder decides licensing. No publishing or redistribution occurs.
- **Permissions/data:** on load this companion only registers a page, sidebar entry, palette command and status button. It makes no automatic model calls, screen observations, persistent writes, memory/conversation reads, schedules or messaging. **Find profiles** (beside **Bot screen**) explicitly reads registered connection/profile route metadata through `host.profileRoutes()`. Only routes whose actual target is one of the six framework profiles are selectable; a framework-named alias cannot authorize another target.
- **Screen access:** after a separate route selection and **Open screen** click, `host.openScreen()` revalidates the route and connection and opens the bundled native viewer. The viewer contacts that configured backend; opening an already-running display attaches live frames, and revealing an existing tab may retain its current control lease. Starting a display, taking over, handing back and pasting remain separate native controls. Closing the tab stops its viewer; hiding it is not a guarantee that streaming stops. This is a post-boot per-profile desktop, not a VM boot/install console or proof of VM power state. Missing routes/providers and read/open failures must remain visible, without an active-profile, local-host or external-viewer fallback.
- **Other manual controls:** the **Quick links** rows navigate to the separate Hunting Lab page, the Hunt Board page, Kanban, the profile manager or the browser, and the last row optionally asks the existing visible pet to display a fixed reminder. Opening Hunting Lab does not pull images or start containers; its separate explicit human Start controls the lab. Native destinations can independently access data or dispatch work; use only approved connections and synthetic/sanitized evidence.
- **Important limit:** the desktop SDK is powerful and is not a sandbox. These source-level restrictions are not a host-enforced permission boundary. Profiles and VMs alone do not establish an approved target-execution sandbox.
- **Enablement:** a standalone desktop plugin loads enabled by default in the supported host. Install only into an explicitly selected Hermes home, never an unrelated specialist profile. Do not alter disabled-plugin preferences or rewrite SOUL files to get development access. A fresh source copy is not proof the renderer mounted it.
- **Other candidates:** bundled Kanban and Bot Mode are retained, not reinstalled. Existing advanced-delegation is unchanged. Radio, trading, RSS feeds, messaging catalog entries, external gateways, image-generation plugins and pet catalog assets are not installed/enabled. Each future third-party candidate needs its own origin/version/license, execution permissions and destination/data review.

## Destination prerequisites

1. Approved OS/architecture with a supported native Hermes Desktop release and plugin SDK (`ROUTES_AREA`, `SIDEBAR_NAV_AREA`, `PALETTE_AREA`, `Button`, `atom`, `useValue`, `host.navigate`, `ctx.register`). Screen opening additionally requires `host.profileRoutes()`, `host.openScreen()` and the enabled bundled Bot Screen provider from the reviewed native source changes. Installing this companion alone does not add those APIs or update an existing Desktop binary. Apply the reviewed native patch to its documented source base and build that Desktop separately; verify the built app before claiming Screen support. The `ctx.runAction` and `ctx.pet` helpers are feature-detected. Unsupported actions visibly report unavailable; no fallback is attempted.
2. Python 3.9+ with SQLite for the ledger and optional installer; Node for executable plugin contract tests. Optional LangGraph/LangChain dependencies remain separate. No OMP installation is required by the product.
3. Stable native profiles installed through normal `setup_hermes.py install`; existing exact authored profiles are preserved and new ones use native confirmation. The companion-only helper never clones, resets, deletes or broadens a profile. Use an approved general development session, not an analyst identity that prohibits development.
4. **For model hunts only:** independently configured provider access on the native `anthropic` provider (Claude Pro/Max OAuth) with reviewed routes: coordinator and independent reviewer on `claude-opus-5-5`; researcher, builder, librarian and Network Analyst on `claude-sonnet-5-5`. Inspect execution metadata; never substitute a destination's available model. UI/lab controls need no provider credential.
5. Approved synthetic or sanitized evidence only. Network Analyst receives human-approved summaries or, in a tool-driven lab hunt, its owned read-only lab tools: case-scoped Arkime metadata and `packet_fields`, decoded allowlisted fields of the case's saved capture with secrets removed. Never live capture, raw packet bytes, tool views or direct Arkime access. Workspace navigation itself needs no Arkime/Wireshark connection. The separately human-started [built-in lab](../README.md#built-in-local-hunting-lab) pulls its pinned container images under its own explicit controls.
6. A human controls scope → evidence/hypotheses → analysis → independent review → handoff. Native Kanban is not the approval ledger. Knowledge/memory promotion is a separate human decision; no automatic trusted-memory writes.

## Use and removal

Normal `setup_hermes.py install` includes this companion and the Hunting Lab. The narrower `python install_desktop.py check` and `python install_desktop.py install --home <approved-general-Hermes-home>` remain companion-only controls (`py -3` on Windows, `python3` on macOS/Linux). The home and ancestors must be ordinary directories, not symlinks/reparse points. Updates require the framework ownership marker and matching old file hashes; unknown files, user edits and aliases are refused before replacement. The companion helper writes only its fixed source and ownership metadata, never configuration or a database. These checks are not a same-user filesystem-race sandbox.

Use the native **Open cybersecurity workspace** palette entry or sidebar entry. A compatible app watches the desktop plugin directory; if absent, use native **Reload desktop plugins**. Hot-reload availability is not a reason to restart/kill the user's app. Disable through native plugin controls; do not remove profiles or databases. This run does not automatically open Kanban, browser, HUD, memory graph or any sensitive view.

## Desktop core hook: plugin tool cards

The Hunting Lab's `lab_browser` card needs one small Desktop core change (`apps/desktop`, branch `feat/desktop-tool-card-hook`), shaped to be upstreamable on its own:

- **API:** `TOOL_CARD_AREA` (`'transcript.toolCard'`) from `@hermes/plugin-sdk`. A plugin registers `ctx.register({ id, area: TOOL_CARD_AREA, data: { tool: '<exact tool name>', render } })`. `render(props)` receives `toolName`, `toolCallId`, `args`, `status` (`running` / `complete` / `error`), `result` (JSON-decoded), `sessionId`, `profile` (the chat's owning profile: a Bot tile's own profile, else the session's known owner route; null when unknown), `resolveImageUrl(path)` (the same authenticated media read the generic row's thumbnail uses) and `fallback` (the generic row). Returning `null` keeps the generic row.
- **Ownership:** one owner per tool name. The earliest registration holds it until it unregisters; a later claim (whatever its `order`) is refused with a `[tool-card] refused …` console warning. Core's own surfaces (built-in cards, file-edit diffs, silent tools) can never be claimed.
- **Rendering:** `ChainToolFallback` consults the owner before the built-in card path; `isCardTool` counts claimed tools as cards, so they are never folded into a run summary. The plugin render runs inside an error boundary whose fallback is the generic row. A call sealed without a result keeps the generic row, as the built-in cards do.
- **Gateway:** no change. `lab_browser`'s `tool.start` / `tool.complete` reach the desktop under the default `display.tool_progress: all`; with `tool_progress: off` the gateway drops them and no card (or row) appears.
- **Hunting Lab use:** the plugin claims `lab_browser`, reads `TOOL_CARD_AREA` off the SDK namespace (an older Desktop keeps the generic row), shows `http://127.0.0.1:8790/live/<profile>.mjpg` while the call runs, then the call's own final frame (`result.image_path`, written by `lab_browser` under its browser folder) or the board's latest `.jpg`. The profile is `result.profile` once the call returns, else the chat's owning profile. The card is one raised box: a header with a globe icon, the status shape (working arc, done check, failed dot in the blocked hue), `lab_browser`, the action in monospace and `running`/`done`/`failed` with the elapsed time this card observed (none for a call first drawn already settled); then the call's arguments and profile while running, the page's title, URL, element count, blocked requests and image path when done, or the arguments, error and profile when failed. The frame is a 168 × 100 thumbnail beside the facts and is left out, not drawn empty, when no frame loads (for example while the board is not serving that browser).

## Branding and future white-label work

Cybersecurity semantics are isolated in `desktop/cybersecurity-workspace/` and the six existing bot definitions. The UI uses the host's theme variables and Lucide icon paths (ISC notice in each plugin source); it draws no logo, creator artwork, trademark mascot or downloaded pet. The `hunt-lab` plugin also contributes an optional dark **Hunt Command** Desktop theme through `THEMES_AREA`, set to the approved canvas surfaces (rail `#0e0e0e`, chrome `#121212`, pane `#161616`, raised `#1c1c1c`) with white ink and a blue focus ring. Product branding/trademarks are not granted by a source license. Before a future white-label release, separately review the framework's distribution license, Hermes notices/trademarks, dependency license inventory, video attribution and all asset licenses. Keep that decision separate from cybersecurity policy and from any knowledge/memory promotion. The portable kit is a local source artifact, not a release authorization.
