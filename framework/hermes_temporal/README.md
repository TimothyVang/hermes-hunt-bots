# Native Hermes workflows with Temporal

This optional package adds durable, human-gated orchestration around the existing native Hermes CLI. It does not replace Bot Mode, change Hermes delegation, call a model/provider from a workflow, or alter the manual ledger or LangGraph observer. Within a step, native Hermes and its configured profile remain responsible for their normal delegation behavior.

## Install and start the local development service

Python 3.10+ is required by the pinned Temporal Python SDK. Run these commands from the `framework/` directory in this workspace, or the extracted `hermes-bot-framework/` directory in the portable ZIP. Install into a dedicated project-local environment:

```powershell
py -3.13 -m venv .venv-temporal
$python = (Resolve-Path '.\.venv-temporal\Scripts\python.exe').Path
& $python -m pip install -r .\hermes_temporal\requirements.txt
```

```sh
python3 -m venv .venv-temporal
python="$PWD/.venv-temporal/bin/python"
"$python" -m pip install -r hermes_temporal/requirements.txt
```

The SDK pin is `temporalio==1.35.0`, a published release. The file also pins `websockets==15.0.1` (the version Hermes pins), which only the hunt board's optional live browsers use. These are direct dependency pins, not a transitive hash lock. Start a Temporal **local development server** explicitly using Temporal's official development-server procedure, listening only on loopback (default `127.0.0.1:7233`). Do not use Temporal Cloud or supply cloud credentials/configuration. A worker is required for workflows to progress; start it from the same source-kit directory with `"$python" -m hermes_temporal.worker` (PowerShell: `& $python -m hermes_temporal.worker`). This starts disabled by default and makes no Hermes dispatch unless the explicit execution flags below are supplied.

## Synthetic input and workflow control

The worker defaults to **refusing all Hermes execution**. When it is running with Hermes execution disabled, workflow status and human decisions require no model credentials, and any approved execute gate is refused without dispatch. To enable actual dispatch, use only the separately prepared synthetic VM/home and supply all explicit absolute paths (`.bat`/`.cmd` wrappers are refused):

```powershell
& $python -m hermes_temporal.worker --enable-hermes --hermes-executable 'C:\approved\path\hermes.exe' --hermes-home 'C:\approved\separate-hermes-home' --working-directory 'C:\approved\synthetic-work' --receipt-db 'C:\approved\state\hermes-receipts.sqlite3'
```

The receipt SQLite file must remain durable and be shared by every worker on that host; independent or lost receipt stores remove dispatch protection. It is coordination data, not a sandbox. Each step's Temporal activity deadline is longer than the native subprocess deadline to allow receipt and process cleanup. Timeout terminates only the direct CLI child; gateway/native delegation may continue. Native output is capped at 65536 bytes, native turns at 32, and empty or invalid UTF-8 output is treated as unknown. The execution process does not inherit host provider keys or the user PATH: PATH is restricted to the explicit executable directory plus OS system paths. HOME, HERMES_REAL_HOME, USERPROFILE, APPDATA, LOCALAPPDATA, CODEX_HOME, XDG config/data/cache/state/runtime directories, PYTHONUSERBASE, TMP, TEMP, and TMPDIR are pinned under `<approved-hermes-home>/.temporal-process/`. Separately provision any needed native credentials in that isolated Hermes home; never copy host credentials.

The worker drains Hermes's stderr while the step runs and keeps only its last 4 KiB, so a chatty process never blocks on a full pipe. When a step ends `native_nonzero`, `output_unavailable` or `subprocess_timeout`, its result carries `diagnostic`: the exit code plus one cause from that tail, for example `exit code 1: RuntimeError: provider closed the stream` (or `exit code 1; no stderr`). When the provider refused the step, Hermes says so only in the profile's `logs/agent.log`, tagged with the session ID; the worker then looks up that session there (last 4 MiB) and the diagnostic reads `exit code 1: model declined to respond (finish_reason=content_filter, category cyber)` instead of a stderr line. The last Python exception line is preferred, then the last line saying error, fatal or failed, then the last three lines. The cause is reduced to printable ASCII, cut at 600 characters, and stripped of anything that looks like a secret: `Authorization` and cookie values, bearer and basic credentials, `api_key`/`token`/`secret`/`password`-style values (after `:` or `=`, or a quoted value after a space, as in `api_key "..."`), `sk-`/`pk-`/`rk-` keys, `sk_`/`pk_`/`rk_` keys that contain a digit (as in `sk_live_...`; `pk_receipts` stays readable), `xox?-`, GitHub, GitLab, Hugging Face, AWS and Google key shapes, JWTs, URL user info and query strings, and long base64 or hex runs that contain a digit. Redaction is pattern-based, so treat a diagnostic as operator data, not as text to publish. Only stderr is read for it; stdout, which carries the model's text, never is. Successful and `output_limit` results carry no diagnostic. `status` prints it with each result, and the Hunt Board shows it after the reason code: on a dropped step's line under the timeline and on the step's card in the Round record (`/state.json` has it as each step's `result.diagnostic` and each feed item's `diagnostic`). The receipt stores it in a `diagnostic` column, so a repeated execution ID returns `previous_dispatch_unknown` with the first run's diagnostic; a worker adds the column to an older receipt database when it opens it, and receipts written before that have none. `diagnostic` is an optional field with a default: Temporal's JSON converter decodes results recorded before this change with `diagnostic: null`, and code without the field ignores it, so existing histories replay unchanged.

By default the worker refuses the operator's own live Hermes home (`~/.hermes` or `%LOCALAPPDATA%\hermes`) and requires a separately provisioned one. To deliberately reuse the operator's existing native sign-in without copying credentials, add `--allow-operator-home` and pass that home as `--hermes-home`. The opt-in changes only that home check; profile policy, turn caps, receipts and every human gate still apply. Native runs then share that home's profiles, sessions and logs, and `.temporal-process/` is created beneath it.

`--record-usage` makes the worker run each step with Hermes's `--format stream-json` output and keep only its final `result` record. The step's output is then that record's text, and its result carries `usage` (`input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens`, `total_tokens`, `duration_ms`) and the native `session_id`; status prints them and the receipt stores them. Where a failed run still reports usage, the result keeps it so spend is accounted for. The raw stream is bounded at 16 MiB and one line at 1 MiB; the final text keeps the 65536-byte cap. Without the flag the command and its parsing are unchanged. A receipt file opened by this version gains two nullable columns, and a worker running older code cannot reserve in it afterwards, so do not share one receipt file between old and new workers. Measured on the lab home on November 9, 2026: one tool-driven Threat Hunter step completed in 177 seconds with 19 lab tool calls and reported 328,152 input tokens (284,905 cache reads) and 13,011 output tokens.

`--activity-threads N` (1 through 32, default 4) sets how many steps one worker runs at the same time. Start a worker for a parallel hunt with at least as many threads as its widest wave; steps beyond that wait for a free slot while their activity deadline runs.

Set matching `--address` and `--task-queue` on both CLI and worker when overriding defaults. Both entrypoints reject non-loopback addresses before connecting. Accepted hosts are `127.0.0.1`, `localhost`, and `[::1]`, with a port from 1 through 65535. The defaults are `127.0.0.1:7233` and `hermes-temporal`.
For the standalone `start` command, prepare a UTF-8 JSON file containing synthetic content only; never include credentials, sensitive/private evidence, real incident data, or secrets in Temporal input. Its object must set `synthetic_only` to `true`. The one-step `start` example follows the hunt instructions below.
The only permitted native Hermes profiles are `framework-coordinator`, `framework-researcher`, `framework-builder`, `framework-reviewer`, `framework-librarian`, and `framework-network-analyst`. Delegation remains within the profile's native Hermes turn; there is no workflow-level model or provider routing.

### Start a supplied-evidence hunt

`hunt` constructs the fixed nine-stage hunt from a UTF-8 JSON file. The command reads that JSON file only; evidence is supplied as inline text and locator strings are labels for citation, not paths or fetch instructions. No locator is opened, resolved, or fetched. Use invented, benign content only: `synthetic_only` is an assertion required to be `true` if present (it defaults to `true`), **not** content sanitization or proof the evidence is synthetic. Do not submit real incident data, private/controlled evidence, secrets, or credentials.

The input object accepts exactly these top-level fields:

- `scope` (required): nonempty string, at most 4096 UTF-8 bytes.
- `evidence` (required): array of 1–32 items, each with exactly `source_id`, `locator`, and `content`. Each is a nonempty string of at most 64, 256, and 8192 UTF-8 bytes respectively. `source_id` values must be unique. At least one locator must begin with `dns-lab-001:`, `dns-lab-001/`, `hunt_lab:`, or `hunt_lab/`, or with the ontology's own `case_id` (a `[a-z0-9-]{3,64}` ID) followed by `:` or `/`, identifying a bounded summary source. This check does not validate or retrieve the referenced source.
- `approval_timeout_seconds` (optional): integer 1–86400; defaults to 3600 seconds for each human wait.
- `synthetic_only` (optional): must be the boolean `true`; defaults to `true`. Only a `data_origin` input sets it to `false`.
- `data_origin` (optional): absent for synthetic data; otherwise exactly `"public-dataset"` or `"work-export"`, accepted only with `"mode": "tool_driven"` and `"synthetic_only": false`, and refused when the scope or `stage_guidance` calls the data synthetic. See **Real-data cases** under [Tool-driven hunt](#tool-driven-hunt-over-the-loaded-lab-case).
- `ontology` (optional): a version-1 snapshot as described below. Supplying it enables ontology-scoped prompts and strict output-handoff validation.
- `context_by_step` (optional): a stage-to-evidence-ID map; only valid with `ontology`, as described below.
- `mode` (optional): `inline` (the default, described here) or `tool_driven` (see [Tool-driven hunt](#tool-driven-hunt-over-the-loaded-lab-case)).
- `parallel` (optional): boolean, default `false`. See [Parallel hunts](#parallel-hunts).
- `follow_ups` (optional): integer 0–12, default 0; accepted only together with `"parallel": true` and `"mode": "tool_driven"`, and refused otherwise, even as 0. See [Parallel hunts](#parallel-hunts).

Unknown fields, missing/empty required values, invalid types, duplicate source IDs, or out-of-bounds text are rejected. The assembled prompts are also bounded: at most 65536 UTF-8 bytes in total (262,144 for a hunt with follow-ups; see [Parallel hunts](#parallel-hunts)), with no prompt over 65536 bytes. The hunt example below contains only invented benign fixture text:

```json
{
  "synthetic_only": true,
  "scope": "Invented DNS-lab summary only; identify uncertainty, no external access.",
  "approval_timeout_seconds": 3600,
  "evidence": [
    {
      "source_id": "demo-dns-1",
      "locator": "dns-lab-001:summary/demo-1",
      "content": "Invented example: host demo.invalid queried example.test once; no alert outcome is asserted."
    },
    {
      "source_id": "demo-note-2",
      "locator": "fixture:note/demo-2",
      "content": "Invented note: the query may have been a test; no operator confirmation is asserted."
    }
  ],
  "ontology": {
    "schema_version": 1,
    "case_id": "demo-case",
    "entities": [
      {
        "entity_id": "host:demo",
        "kind": "host",
        "label": "Invented demo host",
        "evidence_ids": ["demo-dns-1"]
      },
      {
        "entity_id": "domain:example-test",
        "kind": "domain",
        "label": "Invented queried domain",
        "evidence_ids": ["demo-dns-1", "demo-note-2"]
      }
    ],
    "relations": [
      {
        "relation_id": "rel:demo-query",
        "subject_id": "host:demo",
        "predicate": "resolves_to",
        "object_id": "domain:example-test",
        "evidence_ids": ["demo-dns-1"]
      }
    ]
  },
  "context_by_step": {
    "evidence": ["demo-dns-1"],
    "intel": ["demo-note-2"]
  }
}
```

The optional `ontology` snapshot has exactly `schema_version`, `case_id`, `entities`, and `relations`; version is integer `1`. Entities have exactly `entity_id`, `kind`, `label`, and `evidence_ids`; relation objects have exactly `relation_id`, `subject_id`, `predicate`, `object_id`, and `evidence_ids`. Entity kinds are `host`, `account`, `address`, `domain`, `key`, `process`, `session`, `service`, or `resource`; predicates are `associated_with`, `observed_on`, `communicates_with`, `resolves_to`, or `spawned`. IDs use the safe form `[A-Za-z0-9][A-Za-z0-9_.:-]{0,127}` and are stable supplied identifiers, not generated facts. Each entity/relation cites one or more exact supplied `source_id` values; relation endpoints must exist. The complete snapshot is limited to 32 KiB UTF-8, 64 entities, and 128 relations; IDs/case ID are at most 128 UTF-8 bytes, labels 1024 bytes. Unknown/missing fields, invalid/duplicate IDs or references, unsupported values, malformed JSON-compatible values, or unresolved endpoints are rejected.

`context_by_step` is optional and requires `ontology`. Its keys are existing stage IDs; each value is a nonempty list of distinct exact evidence `source_id`s from the input. Omitted stage keys use all supplied evidence except `network`, which defaults to the existing bounded DNS/hunt-lab locator subset. `network` can select only that subset. For each step, the prompt identifies the selected IDs and count of omitted supplied evidence, includes only selected inline evidence, and supplies a snapshot filtered to entities whose full evidence-ID set is selected, then relations whose own references and both endpoint entities are selected; canonical IDs are preserved and unsupported context omitted. This scopes initial inline evidence/snapshot only: later prompts separately receive actual completed outputs from their declared direct predecessors only after a human review. It does not automatically redact those outputs or establish a security boundary. Evidence locators remain labels, never retrieval instructions.
With `ontology`, the constructor also attaches each step's exact `{ "snapshot": ..., "evidence_ids": [...] }` value as `HermesStep.hunt_context`; without ontology, `hunt_context` is `None` and existing free-text output behavior is unchanged. `HermesStep` validates the context shape and snapshot. The standard-library-only [`ontology.py`](ontology.py) module exports `validate_snapshot`, `select_snapshot`, `validate_handoff`, and `handoff_instructions`; this validates structure/references, not factual truth. Native Hermes receives JSON instructions in the prompt, but those instructions alone do **not** enforce a native chat's output schema.

An ontology-enabled completed turn must return one strict JSON object (no Markdown fences, duplicate object keys, `NaN`, or `Infinity`) with exactly these fields: `schema_version: 1`, `case_id`, `step_id`, `profile`, `claims`, `reviews`, `disposition`, `limitations`, and `requested_decisions`. A claim is exactly `{claim_id, kind, statement, evidence_ids, entity_ids, contradicts}`; kinds are `observed`, `inference`, `hypothesis`, or `finding`. Claim IDs are unique and namespaced with the exact current step ID plus `:`. Evidence/entity IDs must resolve in that step's selected context; contradictions may target only another current or reviewed predecessor claim, and in histories started with patch `handoff-ancestor-contradictions-v1` also a claim of any other human-reviewed earlier step of the same workflow (a step sees those quoted in its predecessors; unknown targets and self-contradiction stay rejected, and such a claim is never a review target). A review is exactly `{review_id, claim_ids, disposition, rationale, evidence_ids}`, namespaced the same way; only `framework-reviewer` may provide reviews, whose dispositions are `needs_revision`, `needs_validation`, or `review_ready`; other profiles must return `reviews: []`. Handoff disposition uses those same three values. Bounds are 16 claims and 16 reviews; IDs are at most 192 bytes, claim statements and review rationale 2048 bytes, evidence/entity/contradiction/claim reference lists at most 32/64/32/32 items, and `limitations` and `requested_decisions` each allow at most 16 strings of 512 bytes. The whole handoff is at most 16 KiB UTF-8. Reviews and requested decisions are recommendations, never human approvals or verified truth. Unknown/missing fields or any invalid citation/identity/contradiction rejects the handoff rather than silently dropping data. In histories started with patch `handoff-explained-rejections-v1`, rejection messages say what to fix using only workflow facts and ID-shaped values: the missing or unexpected fields of a handoff, claim or review, the expected `step_id` and `profile`, the expected ID prefix or the duplicated ID, the offending claim ID with the allowed kinds, and the rejected contradiction target with its claim (fixed text first, since the correction notice keeps 300 characters); older histories keep the messages they recorded, because a reason is part of the retry prompt. Tool-driven hunts' JSON instructions also state that nothing may follow the JSON, that a review has no `claim_id` key, and that contradictions may target any human-reviewed earlier step; inline hunts keep their original wording.

Validation occurs after the native execution has completed and before its human review gate or use as a predecessor. Invalid output (a JSON parse error or a `validate_handoff` rejection) gives that step one correction retry in histories started with patch `handoff-retry-once-v1`. The retry is a new execution, not a blind redispatch: the workflow returns to `awaiting_execution_approval` for the same step and waits for a fresh human execute decision with a new decision ID (the first approval's ID is ignored). It then dispatches under execution ID `<workflow_id>:<index>:retry` with the original prompt plus a short correction notice. The notice quotes the validator's own error message, ASCII-escaped and cut to 300 characters, and asks for one corrected JSON handoff; in histories started with patch `handoff-retry-whole-check-v1` it also asks the model to check every claim and review against all the rules, not only the reported error. A second rejection ends the workflow at terminal `handoff_validation_rejected`. So does a first rejection when the notice would push the prompt past 65,536 UTF-8 bytes, and a first rejection in a history started before the patch. Status lists every rejection in `handoff_rejections` as `{step_id, reason, outcome, result}`, where `outcome` is `retried`, `retry_exhausted`, `retry_prompt_too_large`, or `retry_unavailable` and `result` is the rejected completed execution, kept as an execution fact rather than a fabricated native failure. `results` keeps one entry per reached step: a retried execution moves out of `results` into its rejection record, and a terminal rejection stays as the last result, as before. Valid output still requires a separate human review decision. Only a direct predecessor with a completed, valid, human-reviewed handoff is passed as prior claims/context (plus, after a dropped `merge`, its reviewed follow-ups; see [Parallel hunts](#parallel-hunts)); that passed output is separate from selected initial inline evidence. The durable dispatch fingerprint includes `hunt_context`, so reusing an execution ID with a changed context is a fingerprint conflict, not permission to dispatch again.

Typed collaboration budgets are allocated deterministically before the first gate or activity. Each downstream prompt reserves its UTF-8 base prompt, exact predecessor framing, and any output-cap disclosure. It then reserves each typed producer's minimum compact valid JSON envelope using its exact case, step, and profile identity, empty collections, and the shortest valid disposition (`review_ready`). If those minima cannot fit, even a positive remaining budget is rejected before any execution approval or dispatch. Remaining headroom is divided conservatively across predecessors (up to 16,384 bytes each); a producer serving multiple typed consumers gets the tightest assigned cap. Untyped predecessors do not acquire a JSON schema requirement. The producer prompt discloses its cap before generation. A completed result above its assigned raw UTF-8 byte cap remains visible as a truthful `completed` execution result and is never forwarded. In a serial workflow it ends at `output_limit_rejected` before review. In a parallel workflow (patch `output-cap-retry-once-v1`) the step first gets one corrected re-run behind the wave's retry execute gate, told its measured size, the hard limit and a target of half the cap; the over-cap result is recorded as a `retried` handoff rejection, and a second over-cap result ends at `output_limit_rejected` (dropped if the step is optional). No output or citation is truncated or omitted, and all-untyped legacy workflows retain their previous behavior.

The cap calculation and prompt disclosure use a Temporal patch marker (`typed-handoff-output-budgets-v1`): histories created before this change replay the legacy path, while new histories use the bounded path. This preserves replay compatibility for existing executions; do not reset or rewrite histories to opt an existing execution into the new behavior.

The isolated fan-in verification reproduced the archived baseline failure with five individually valid 16,300-byte outputs: the analysis prompt reached 84,093 bytes and was rejected before its activity. After the minimum-envelope fix, a real loopback Temporal smoke completed all nine stages with 18 explicitly simulated execute/review decisions and exactly one scripted activity per stage. Outputs filled the advertised caps; the analysis prompt was 65,534 bytes. A response one byte above its 12,555-byte cap ended at `output_limit_rejected` before review while retaining its completed execution fact. A positive 100-byte predecessor budget rejected before any activity. Temporal Replayer also accepted the 95-event history retrieved from the original baseline SQLite store against the new code.

The targeted workflow, ontology, receipt, and hunt gate passed **45 tests, zero skips, exit 0** (14.398 seconds reported by unittest). The owned runner substituted the existing local Temporal CLI for the time-skipping server factory to avoid downloads. An initial run exposed two test-helper early-signal races; the helper now waits for the execution gate before signaling, and the corrected gate passed. Evidence is retained under `<user-temp>\hermes-fanin-proof-x6pwnni7` in `baseline-evidence.json`, `afterfix-evidence.json`, `baseline-history.json`, and `targeted-tests-evidence.json`. All fixtures and decisions were synthetic, no Hermes subprocess or provider was invoked, and workers/servers were shut down. These checks do not establish actual model work, human authorization, or a completed native hunt.


Start with an explicit, unique workflow ID; creating/starting the workflow does **not** authorize or perform a paid Hermes execution. Each stage pauses for a human execute approval before dispatch and a separate human review after the result. Denial or timeout stops progress. For example:

```sh
"$python" -m hermes_temporal.cli hunt synthetic-hunt-002 --input ./synthetic-hunt.json
"$python" -m hermes_temporal.cli status synthetic-hunt-002
"$python" -m hermes_temporal.cli decision synthetic-hunt-002 --step-id scope --phase execute --choice approve --decision-id exec-scope-1
# After the actual native result is inspected:
"$python" -m hermes_temporal.cli decision synthetic-hunt-002 --step-id scope --phase review --choice approve --decision-id review-scope-1
```

### Export the fixed Elastic lab evidence and run finite practice

`lab-input` exports the existing `dns-lab-001` lab query results as a supplied-evidence hunt JSON file. It is a local export only: it makes no Temporal connection, native Hermes dispatch, model/provider call, or VM lifecycle request. Give the exporter a new output path because it refuses to overwrite an existing file:

```sh
"$python" -m hermes_temporal.cli lab-input --state-dir ./approved-lab-state --output ./synthetic-lab-hunt.json
"$python" -m hermes_temporal.cli practice synthetic-practice-001 --input ./synthetic-lab-hunt.json --rounds 3
"$python" -m hermes_temporal.cli practice-status synthetic-practice-001
```

The lab must already be prepared and running through the human-operated lab controls before exporting its actual bounded case/events/network responses; `lab-input` does not start it. The export contains supplied evidence and optional ontology only, not scoring truth. Keep the operator-only score truth outside Temporal inputs and the Hermes worker environment.

`practice` runs a finite parent loop over the same supplied fixture, defaulting to three rounds (allowed range 1–10). Every round is a separate existing hunt workflow, with exact child workflow IDs `PARENT_ID:round:NNN` (for example, `synthetic-practice-001:round:001`). Each hunt retains its human execute approval and separate human review at every stage. Use the existing `decision` command with the exact child ID as the workflow ID; for example:

```sh
"$python" -m hermes_temporal.cli decision synthetic-practice-001:round:001 --step-id scope --phase execute --choice approve --decision-id practice-001-r001-exec-scope
"$python" -m hermes_temporal.cli decision synthetic-practice-001:round:001 --step-id scope --phase review --choice approve --decision-id practice-001-r001-review-scope
"$python" -m hermes_temporal.cli practice-stop synthetic-practice-001
```

Do not treat replaying the same fixture as a holdout evaluation or proof of improvement; inspect and compare actual round outputs, with operator-only truth used only for separately authorized scoring. The parent proceeds only after a completed round and stops on any non-completed outcome. A stopped/closed parent does not prove that an in-flight child, Hermes process, or delegated descendant stopped; inspect actual child workflow state and approved runtime evidence. Uncertainty never authorizes replay. Practice adds no global spend cap: each execute gate remains a human authorization point and requires an actually ready backend and bounded provider authorization. The worker remains disabled by default. These new features are not live-verified; documented commands are not evidence of a successful deployment or run.

The parent workflow timeout is computed before execution: for each round, it sums `3 × approval_timeout_seconds + step.timeout_seconds + 140 seconds` for every untyped hunt step and `4 × approval_timeout_seconds + 2 × (step.timeout_seconds + 140 seconds)` for every structured (ontology) step, then multiplies that per-round total by the requested round count. The approval windows account for possible execute, review, and reconciliation waits, plus the execute wait of a structured step's one handoff-correction retry; `140` seconds is the activity schedule-to-close allowance, counted once more for the retry. This is a finite upper bound for the workflow's configured gates/activities, not a provider spend cap or guarantee that downstream Hermes work stops when the parent ends.

### Tool-driven hunt over the loaded lab case

With `"mode": "tool_driven"` the bots query the lab themselves instead of reading exported records. The only inline evidence is the case metadata item, with locator `<case_id>:summary/case`; the input must also carry an `ontology` whose `case_id` is that same `[a-z0-9-]{3,64}` case ID (an empty entity/relation list is fine), so every stage returns a validated handoff. Any other evidence item, a locator for another case, or a missing ontology is refused. Export one for whatever case the analyst VM has loaded:

```sh
"$python" -m hermes_temporal.cli lab-input --tool-driven --state-dir <hermes-home>/profiles/framework-network-analyst/hunt-lab-vm --output ./tool-hunt.json
"$python" -m hermes_temporal.cli practice tool-practice-001 --input ./tool-hunt.json --rounds 1
```

`--tool-driven` reads the VM's loopback `lab_url` through the read-only runtime `status` (it refuses a stopped VM, another owner, or any URL other than `http://127.0.0.1:<port>`), then makes one GET of `/case` with no proxy, no redirects, and a 512 KB cap. It exports no events or sessions. The scope is the tuned brief adapted to tools: at most 10 claims and 6 limitations per stage, list every supporting `event.id` individually in claim statements (past 12 in one series, list 12 plus the exact query and total, but first at least one per distinct process and per `event.category` of each process), give each series' count, interval and span, check a task's domain, and restate coverage gaps, including tool limits.

**Real-data cases.** A case's `case.json` may name its origin. `"data_origin": "public-dataset"` holds real lab telemetry from a public research dataset the operator approved for the lab (`hunt_lab.import_dedale` writes it for DEDALE); `"data_origin": "work-export"` holds a time window of the operator's own unclassified work logs exported from the work Elastic (`hunt_lab.import_elastic` writes it; see [Loading a work export](../README.md#loading-a-work-export)). Both are allowed by HUNT-BOTS.md rule 1. `prepare_guest`, the guest lab service and `lab-input` refuse any other `data_origin` value, and the lab console page names the case's origin. `lab-input --tool-driven` exports such a case only when the operator adds `--data-origin` with the case's own origin (`--data-origin public-dataset` or `--data-origin work-export`); it refuses the case without the flag, refuses a flag naming another origin, refuses the flag on a synthetic case, and refuses the flag without `--tool-driven`. The exported input then carries `"synthetic_only": false` and that `data_origin`, and the bots see one wording per origin, from the single table `DATA_ORIGINS` in `contracts.py`: public research dataset (real lab telemetry, no customer data), or work log export (real telemetry from the operator's environment; unclassified work data). The scope begins `<Name> <case_id> (<detail>) only;`, for example `Work log export work-001 (real telemetry from the operator's environment; unclassified work data) only;`, and the case metadata item and every stage's safety header say that wording instead of synthetic. The header also tells each bot that this statement of the case's origin governs where a tool description or its instructions describe the lab case otherwise. The workflow accepts `synthetic_only: false` only together with one of these origins and a tool-driven request. A synthetic case exports and reads exactly as before, without the flag. In `operator/tool_loops.py`, `base_input(..., data_origin="work-export")` passes the flag; a cached input whose origin differs from `data_origin` is refused.

The coordinator stages (`scope`, `analysis`, `incident`) have no query tools; they may send at most 3 bounded `delegate_task` follow-up questions to the owning specialist profile and must cite the returned findings. That limit, like every instruction, is prompt guidance. The per-bot tool boundary is enforced at runtime: the `hunt_lab` plugin registers only the tools the step's profile owns, so Hermes refuses any other tool name as unknown (see the [framework README](../README.md#built-in-local-hunting-lab)); the coordinator's delegation targets are enforced by the `profile_routes` route list, which Hermes turns into the `profile` enum, and a task with no profile runs as `framework-researcher`. A tool-driven input may also carry `stage_guidance`, a map from stage ID (`scope`, `evidence`, `hypotheses`, `network`, `intel`, `analysis`, `detection`, `purple`, `incident`, and in a hunt with follow-ups `follow` and `merge`) to 1–600 characters of coaching. Each entry is appended, after `Stage guidance:`, to that stage's tool instruction only (`follow` to every follow-up). It cannot replace the safety header, the scope or the tool allowlists, and it still counts toward the aggregate prompt budget. ### Parallel hunts

With `"parallel": true` in a hunt input, or `"parallel": true` at the top level of a `start --input` file, steps whose dependencies are reviewed run together as one **wave**. A step's wave is 1 when it has no dependencies, otherwise one more than the highest wave among them. For the fixed hunt that gives six waves: `scope`; then `evidence`, `hypotheses`, `network` and `intel` together; then `analysis`; `detection`; `purple`; `incident`. A parallel request may hold up to 32 steps; a serial one stays at 16. A request without `parallel` runs exactly as before, and existing histories replay unchanged.

Each wave has **one execute gate and one review gate**, addressed by the gate ID `wave-<n>`: send `decision <workflow> --step-id wave-2 --phase execute --choice approve ...`, and the review decision the same way. One human decision therefore opens or accepts every step of that wave, where the serial path asks once per step. A step ID of the form `wave-<n>` is refused in a parallel request. The status query lists every step in `steps` as `{step_id, state, wave, execution_id, reason}`, with `state` one of `not_reached`, `awaiting_approval`, `working`, `awaiting_review`, `done`, `dropped` or `stopped`; while a wave is open the top-level `step_id` is its gate ID. Match a step to its entry in `results` by `execution_id`, never by position.

A step may be marked `optional` (a `start --input` step field; a parallel hunt input marks `evidence`, `hypotheses`, `network` and `intel`, and with follow-ups every `follow-<j>` and `merge`). An optional step that fails, times out, exceeds its output cap, or returns an invalid handoff twice is **dropped**: it is recorded with its reason, it is never dispatched again, and its dependents receive the line `Dropped predecessor [<step>]: no reviewed output (<reason>).` in place of its output. A step whose optional dependencies were all dropped does not run, and the hunt ends `rejected` with `no_surviving_dependency`, so a lead never reports from zero hunters. That rule ignores an optional dependency whose own dependencies are all optional, an aggregator such as `merge`: `detection`, `purple` and `incident` still run when `merge` was dropped, with its `Dropped predecessor` line in their prompts. In histories started with patch `dropped-merge-follow-ups-v1` that line is followed by the reviewed claims (`claim_id`, `kind`, `statement`) of the aggregator's own reviewed inputs, the follow-ups, taking each follow-up's first claim, then each one's second, and so on, as many as fit the 65,536-byte prompt while leaving room for a correction notice; a follow-up stops at its first claim that does not fit, so a later claim never shows while an earlier one is hidden, and a closing line counts the claims not shown. Those follow-up handoffs also count as the step's reviewed predecessors, so it may review or contradict their claims. An optional step that cannot run under the rule, such as `merge` after every follow-up was dropped, is itself dropped with that reason instead of ending the hunt. A required step keeps the serial rules: failure ends the hunt with the same terminal stage, and an unknown outcome opens the reconciliation gate under that step's own ID.

**Follow-ups.** A parallel tool-driven hunt input may set `follow_ups` to K from 1 through 12. After `analysis` the hunt then adds `follow-1` … `follow-K` (Threat Hunter, `framework-researcher`, optional). Each depends only on `analysis` and has `focus` `["analysis", j-1]`: `follow-j` receives claim j-1 of the reviewed analysis handoff instead of the whole analysis output, pivots on that finding with its own `elastic_search` and `elastic_aggregate` (and `packet_fields` for a finding stated only from network activity) to find and cite every supporting or refuting event, and may return up to 16 claims. For every attack process it cites it is told to aggregate the process's events by `event.category` (`q=process.entity_id:"<guid>"`) and cite each bucket's `sample_event_id`, to follow `process.parent.entity_id` to its children until no new ones appear, and to follow `next_after` pages of its file and network events; it begins each claim's statement with its verdict (malicious, benign or unresolved) and keeps `kind` one of the four kinds. `merge` (`framework-coordinator`, optional, no query tools, depends on every follow-up) consolidates their results into one claim per distinct activity, with the same verdict rule, and carries every cited `evt-` ID forward; `incident` is told to keep one event per category and per distinct process for each attack process, and to spend its delegated questions on a cited process no reviewed result swept. `detection` then depends on `analysis` and `merge`, `purple` on `analysis`, `merge` and `detection`, and `incident` on `analysis`, `merge`, `detection` and `purple`. That gives eight waves: `scope`; `evidence`, `hypotheses`, `network` and `intel`; `analysis`; the follow-ups; `merge`; `detection`; `purple`; `incident`. Follow-ups get the `evidence` stage's ontology context and `merge` the `analysis` stage's; all of them get the 900-second tool-step deadline. A follow-up whose analysis claim does not exist is dropped with `no_focus_claim`; `merge` is dropped when every follow-up was dropped, and the later stages then run without it. With follow-ups the assembled prompts may total 262,144 UTF-8 bytes (256 KiB) instead of 65,536, and each prompt is still at most 65,536 bytes. `stage_guidance` then also accepts `follow`, appended to every follow-up's instruction, and `merge`, appended to `merge`'s; without follow-ups both keys are refused. Without `follow_ups`, or with 0, the request is exactly the parallel hunt above.

`focus` is also a `start --input` step field, `[step_id, claim index]` with an index from 0 through 15, accepted only in a parallel request. The step must itself carry a `hunt_context`, and the named step must be one of its `depends_on` entries and carry a `hunt_context` too, since only a typed predecessor produces the reviewed handoff the claim is taken from; any other `focus` is refused when the request is built.

Handoff retry works per wave: every step of the wave whose handoff failed validation, and whose correction notice fits, is re-run once behind a second `wave-<n>` execute gate, with `:retry` appended to its execution ID. A practice round of a parallel hunt completes when the hunt completes and every required step has a completed execution; dropped optional steps do not halt it.

Limits to know: a typed step's output cap is still divided among everything feeding one downstream prompt, so many hunters feeding one lead each get a small cap; a step can have at most 16 reviewed typed predecessors; and cancelling a workflow in the middle of a wave cancels the wave's activities rather than opening reconciliation. Start the worker with `--activity-threads` at least as large as the widest wave. Verified on November 9, 2026 with the time-skipping test server (57 workflow and practice tests, including waves, drops, retries, reconciliation and the unchanged serial path); see the practice records below for live runs.

### Live hunt board

`hermes_temporal.board` serves **Hunt Command**, a read-only page for watching one practice run. It issues only the same status queries as `practice-status`/`status` (at most once every 2 seconds), plus a read of the current round's Temporal history when the round's status has moved, and never signals, approves, starts, or stops a workflow. Pass the parent workflow ID and the same hunt JSON file the practice was started with:

```sh
"$python" -m hermes_temporal.board --address 127.0.0.1:7233 --workflow-id synthetic-practice-001 --input ./synthetic-lab-hunt.json --port 8790
```

Open `http://127.0.0.1:8790/` (the server binds `127.0.0.1` only and answers 404 to other `Host` names, including `localhost`). `GET /` is one self-contained page with a strict Content Security Policy and no external resources; `GET /state.json` is the derived view; `GET /live/<profile>.jpg` and `.mjpg` serve live browser frames when `--hermes-home` is given (below); every other path is 404 and every other method 405. The page also works inside a sandboxed iframe (`sandbox="allow-scripts"`): `/state.json` adds `Access-Control-Allow-Origin: null` only for requests whose `Origin` is `null`.

The page (`board_page.html`, read once when `board.py` is imported) is **Hunt Command**: a dark, read-only console that fits a 1920×1080, 1512×864 or 1440×900 window without page scrolling; long panels scroll inside. Design sources and screenshots live outside this repo in the workspace's `design/` folder (canvas and build in `design/method-v2/`). It polls `/state.json` every 2 seconds and rebuilds only when the round's content changes. Every value is inserted as text, and the page has no control that acts on the hunt.
- **Top bar:** case ID and round; the Case, Agents and Evidence tabs; state counts, where blocked is awaiting approval or review, idle is pending or not reached, and dropped covers dropped and stopped; Temporal reachability (or "Temporal query failed" when Temporal answers but the status query errors) and lab reachability; and the local time Temporal was last observed. When the bar is crowded it drops the observed time, then the idle, done and dropped counts, keeping all counts in the tooltip. A bottom bar lists the keys of the current view.
- **Case** (`#view=case`): a rail with the case (open wave and counts, or run stage and round wall time) and one row per role (its open step, or step and claim counts). The main column shows the case question, window, round start, wall time, total tokens and mode; then a card for each wave waiting on a human gate (which step waits, that the next wave waits for the gate decision, and up to two of the step's requested decisions, shown as its requests) or, with no gate open, the latest conclusion; then the waves with roles, step and claim counts and wall time, where open waves and the selected step's wave expand into their steps; then the selected step's claims. The details panel shows that step's state and profile, gate, requested decisions (free text the workflow does not check), live screen, and run facts: wave, start and end, duration and attempts, tokens, disposition, limitations and tool calls, plus a failed step's reason and its diagnostic (the cause the worker recorded, such as a provider refusal).
- **Agents** (`#view=agents&agent=<step_id>`): every step in the rail, grouped blocked, working, done (newest first), idle and dropped, or in step order when all share one state. Three panes: the selected agent (the tool calls its profile made inside the step's time window, with a note when another step overlapped on the same profile, then its handoff claims); the live screen of its profile, or of the first profile with frames; and a second agent (the first other working step, else another open step, else the next one listed) as a compact call table.
- **Agent focus** (`#view=agent&agent=<step_id>`): role, profile, wave, state, duration, tokens, claims and disposition; every claim with kind, cited-event count, verdicts and contradictions; reviews; for an unparsed handoff its parse error and raw excerpt; limitations and requested decisions (the first four and three, with Show all); usage; tool calls; and the live screen when the profile has one.
- **Evidence** (`#view=evidence`): the looked-up events per host on a timeline over the case window, the event list (time, ID, host, category, summary and the IDs of the claims citing it), and for the selected event its citing claims, the graph nodes that contain it and an Arkime link when `tools.lab.arkime_url` is a loopback URL. With no events it says why (lab unreachable, nothing cited) and lists the pending lookups.
- **Live screen:** the profile's `/live/<profile>.mjpg` in one `<img>` that polling never recreates. It reads **Live · N frames** only while the screencast is attached, a step of that profile is working and the last frame is under 10 seconds old; otherwise it gives the age of the last frame or why there is none. View only.
- **Keys:** `1` `2` `3` switch views; `/` or Ctrl K searches agents, claims and events; `g` goes to a view, wave or agent (a tree with roll-up counts); `?` lists all keys; Esc closes a sheet, unzooms, returns from agent focus to the panes or clears a filter. Case: `j` `k` move through waves and steps, Enter opens the step or expands the wave. Agents: `j` `k` agent, `h` `l` pane, Enter opens the focused agent, `z` zooms the pane, `b` `w` `d` `i` show only blocked, working, done or idle agents. Agent focus: `j` `k` claim, `c` copies its ID. Evidence: `j` `k` event, `h` cycles a host filter, `c` a category filter. Keys are ignored while typing, Enter or Space on a focused button or row activates that control, and keyboard actions never animate.
- **Completion toast:** when a step turns done while the page is open, a toast names it with its wave and claim count, unless it is the agent in focus, and disappears after 6 seconds. Its entry fade is skipped under reduced motion; nothing else on the page animates.
- **Narrower windows:** at 1100 px and below the details panel narrows to 280 px and the Case rail is hidden; at 960 px and below the title and round text are hidden. At 760 px and below the page is a phone inbox (`#view=inbox`, the default there): gate cards, then working, done, waiting and dropped steps; tapping a step opens its focus view; a bottom bar switches Inbox, Agents, Case and Evidence.
- **Hash:** `view` is `case`, `agents`, `evidence`, `agent` or `inbox`, with `agent=<step_id>` for the agent views; any other value opens Case.

Only outputs of accepted steps and the step currently awaiting review count as citations; a step stopped by output or handoff validation is shown but not counted. Unparseable output is reported with its status and a raw excerpt. The board displays what the bots wrote; it does not verify claims, and approvals are recorded only in the workflow decisions.

`/state.json` (`board_version` 4) carries these derivations: `round` (`started_ms`, `ended_ms`, `source` `temporal` or `first_stage`); per step `name`, `monogram`, `claims` (parsed claim count) and `timing` (`started_ms`, `ended_ms`, `duration_ms`, `attempts`; all unknown when the history could not be read); `team` (per bot: `monogram`, `steps`, `current` open step index, `claims`); `latest_conclusion`; and `browsers` (below).

For a tool-driven input, also pass the lab: `--lab-state-dir <hermes-home>/profiles/framework-network-analyst/hunt-lab-vm` finds the lab serving the input's case (read-only, re-resolved after a failure because ports change on restart): the VM, whose `lab_url` and `arkime_url` come from the runtime `status`, or a connected service (`hunt_lab.connected serve`, see `framework/README.md`), whose port comes from its `hunt-lab-connected/state.json` and whose every answer must carry the instance token named there. The board refuses `ambiguous_lab` when both serve the case, or `--lab-url http://127.0.0.1:<port>` names it directly, optionally with `--arkime-url`. Lab options are refused for inline inputs, and a tool-driven input without one is refused.


Use `--choice deny` for either execute approval or review to stop without advancing. Every signal must carry the exact currently waiting step ID and phase. Decision IDs are idempotency keys: duplicate use does not process another decision, and conflicting reuse is ignored. Signal transport acceptance is not confirmation that the workflow accepted the decision; query `status` for current progress.

**Who decided.** `decision` takes an optional identity that the workflow keeps with the gate: `--decided-by "<name>"` (1 to 200 printable characters; runs of whitespace become one space), `--via cli|slack|automated` (default `cli` with a name) and, with `--via slack` only, `--slack-user <Slack user ID>`. The CLI refuses an incomplete or malformed identity before connecting, and the workflow ignores a signal that carries such an identity. `status` lists every decision a gate took, oldest first, in `decisions` as `{gate, phase, decision, decision_id, decided_by, via, slack_user}` (the evidence note is not repeated); a decision sent without an identity is listed with empty identity fields. The record is behind patch `gate-decider-v1`, which Temporal decides once per run at its first consumed decision: a workflow whose first gate decision was taken by older code lists no decisions at all, even ones taken later by a new worker, while a workflow that had not yet taken a decision when the worker was upgraded records every one. `operator/drive_gates.py` sends its automated approvals as `--via automated` under the operator's or delegating person's name, and the Slack bridge sends the operator's name, `--via slack` and their Slack user ID.

An activity timeout/failure, cancellation while awaiting its result, worker loss eventually surfaced as an activity failure/timeout, or an unclear receipt produces `needs_reconciliation`; the workflow never automatically repeats that step. This does **not** prove that the native child or delegated work stopped. Inspect approved evidence outside the workflow, then either abort:

```sh
"$python" -m hermes_temporal.cli decision synthetic-hunt-001 --step-id review-fixture --phase reconcile --choice abort --decision-id reconcile-abort-1 --evidence-note "Stopped after examining the synthetic execution receipt."
```

or accept a human-observed result with a specific evidence note:

```sh
"$python" -m hermes_temporal.cli decision synthetic-hunt-001 --step-id review-fixture --phase reconcile --choice accept --decision-id reconcile-accept-1 --evidence-note "Observed expected completion in the approved synthetic receipt."
```

Reconciliation notes are assertions by the operator; the system does not authenticate identity or prove that the note is true. Accepting reconciliation is not a blind retry: the same step is not dispatched again, and a separate review approval is required before advancing. The only redispatch is the single handoff-correction retry described above, and it waits for its own human execute approval. A denial, timeout, failure, or abort stops the workflow. Bounded approval timers fail closed. Terminal stages include `completed`, `rejected`, `timed_out`, `aborted`, and `handoff_validation_rejected`. `needs_reconciliation` is a nonterminal stage awaiting a reconciliation decision; it is not a terminal result. Status reports fixed stage, step ID, execution ID, activity results, handoff rejections, and the decisions gates took with who sent them.

An accepted reconciliation leaves the original execution result marked `unknown`; final workflow completion records the subsequent human decision, not proof that the original native action completed.

`status` includes `temporal_status` from Temporal's execution metadata alongside the application's last `stage`. Cancelling at an execution-approval or review gate closes the Temporal execution as `CANCELED`; the query can still retain `awaiting_execution_approval` or `awaiting_review`. Do not interpret that retained stage as a live wait or an unblocked goal. These are sequential observations, not an atomic snapshot. A closed execution cannot be resumed by another decision signal. Termination or loss of the execution does not establish that externally dispatched work stopped; inspect its receipts and approved runtime evidence before authorizing any new workflow.

## Data, security, and limitations

Temporal history persists workflow inputs (including prompts), signal decisions and evidence notes, execution result output, and workflow events for the server's retention period. Treat the Temporal persistence store, dev-server logs, client terminal, and backups as sensitive according to the supplied content. Use synthetic-only data for this integration and do not put secrets or controlled/private evidence into it. The approval caller is not authenticated by this workflow; a decision ID, evidence note and decider identity (`--decided-by`, `--via`, `--slack-user`) are what the sender states, not proof of identity or authorization.

The local activity receipt is coordination state, not an authentication boundary, sandbox, or exactly-once guarantee for arbitrary side effects. If a process loses contact after dispatch, native Hermes or delegated work may continue. A timeout only terminates the direct child under the worker's policy and cannot assert cancellation of downstream delegated activity. Temporal durability does not make arbitrary side effects exactly once. Keep worker execution on the explicitly approved host/VM and rely on the native Hermes runtime's configured profile/delegation, not a workflow model SDK. No scan, schedule, external messaging, remediation, deployment, or other external-effect automation is provided.

The workflow implementation uses deterministic Temporal workflow APIs, a durable timer for each human wait, and one activity attempt; uncertain activity outcomes go to human reconciliation rather than retry. The workflow does not read credentials or provider configuration. The CLI defaults to a loopback Temporal address and a dedicated task queue. It sends the supplied prompt into Temporal history by design.
