# Hermes Hunt Bots

A fork of [NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent) that turns the Hermes desktop app into a six-bot threat-hunting team. Each bot drives its own read-only lab tool (Elastic, Arkime, redacted packet fields from the case's saved capture, a threat-intel feed, a detection tester) against invented data in a local QEMU lab VM, and hands its findings to the next bot through validated, human-gated handoffs.

Built in the open. This file is the project's rulebook: **every contributor, human or AI agent, follows it, and it overrides upstream guidance where they conflict.**

## What is here

| Path | What it is | License |
|---|---|---|
| `framework/` | The six-bot team: lab tools, Temporal workflows, hunting lab, scenario generator and scorer, Hunt Board, benchmarks, tests. Start with [framework/README.md](framework/README.md). | AGPL-3.0 ([framework/LICENSE](framework/LICENSE)) |
| `operator/` | Operator tools around the hunts: the watcher improvement loop, case switching, the opt-in delegated gate driver, rejection diagnosis, the tool cam and honest video assembly. They read operator-only answer keys, so nothing here feeds bot prompts. See [operator/README.md](operator/README.md). | AGPL-3.0 ([framework/LICENSE](framework/LICENSE)) |
| Everything else | Hermes 0.23.0 (upstream commit `2bd378ed`) plus our reviewed desktop fixes | MIT ([LICENSE](LICENSE)) |
| `../runtime/` (next to the clone, never inside it) | Your local lab: Hermes environments, the VM, cases, answer keys, runs. The lab refuses VM state inside any Git repository. | — |

Copied third-party code keeps its own license and notice, listed in `THIRD-PARTY-NOTICES.md`.

## Rules (enforced)

**Safety.** These are not negotiable, and every PR review checks them (see [Review](#review)).

1. **Synthetic data, an approved public research dataset, or the operator's unclassified work logs.** Cases are synthetic; a public research dataset the operator approved for the lab (DEDALE, decision D7 in the planning notes); or a time window of the operator's own unclassified work logs, exported from the work Elastic or served live by the host-side connected service (planning tickets 01 and 06, ADR 0005). A real-data case names its origin in its `case.json`: `"data_origin": "public-dataset"` (written by `hunt_lab.import_dedale`) or `"data_origin": "work-export"` (written by `hunt_lab.import_elastic`), or `"data_origin": "work-connected"` (served only by `hunt_lab.connected`; `prepare_guest` refuses to seed it into the VM). `lab-input --tool-driven` refuses such a case unless the operator passes `--data-origin` with that same origin, and refuses the flag for a case of any other origin; its hunt is then marked `synthetic_only: false` and tells the bots its origin, never synthetic: a public research dataset (real lab telemetry, no customer data), a work log export (real telemetry from the operator's environment; unclassified work data), or a work log connection (live read-only queries of the operator's work Elastic; unclassified work data). Cases, datasets, work exports and answer keys stay in `runtime/`, next to the clone, and are never committed. No other real data: never customer data, and never CUI/NSS data without a named, approved boundary for it. Never commit real logs, packet captures, credentials, API keys, tokens, cookies, session stores, or anything marked CUI/NSS.
2. **Tools stay read-only and lab-local.** Bot tools may only read the loaded case through a lab service on `127.0.0.1`: the guest's, or, for a connected case, the host-side connected service (`hunt_lab/connected.py`, ADR 0005 in the planning notes), which alone holds the read-only work API key. One resolver (`hunt_lab/endpoints.py`) picks the lab serving the case, refuses `ambiguous_lab` when both do, refuses a connected answer without its instance token, and refuses a connected case while the bot's own environment holds the key variable. No tool may control the VM, capture live traffic, reach other hosts, or read an answer key. `packet_fields` reads only the case's saved capture (`tshark -r` on `evidence/traffic.pcap`), never live traffic, and returns only allowlisted, redacted fields (ADR 0003 in the planning notes); the guest's argument list, field allowlist, filter grammar and URI redaction are enforced and tested with a faked tshark (`framework/test_lab_server.py`). One live run (2026-11-10, generated case `team-med-011`, tshark 3.6 in the guest) returned DNS, TLS and HTTP fields, refused denied fields and filters, answered `field_unavailable` for JA4, and returned every query string among the first 200 HTTP requests as `?[redacted]`. Browser automation may only open lab origins (`127.0.0.1` / `localhost` lab ports); a change that lets a bot browse elsewhere is rejected.
3. **The operator makes two decisions per hunt.** Following the project's accepted decision record on two human decisions per hunt (ADR 0002 in the planning notes, outside this repository), the operator approves the scope before any hunter queries data, and accepts or rejects the final report. The gates between them may be approved automatically; every automated approval is recorded as automated and never presented as human. Response actions remain human decisions. Never fabricate approvals, evidence, model output, scores, or test results. Simulated or scripted runs are labelled as such. Merging code is covered by rule 6.
4. **No real-money trading** and no unattended external actions (messaging, schedules, posting) without explicit opt-in. The bots have no messaging tools. The operator's Slack bridge (`operator/slack_gates.py`, ADR 0004 in the planning notes) is opt-in: it is off unless the operator starts it with their own Slack tokens, and it carries only the operator's own two decisions. Its cards carry bot-written summaries only for synthetic lab cases; real or work data gets ID-and-status cards.
5. **Honest claims.** Docs and PR descriptions state what was actually run and observed. "Enforced" means enforced at runtime, with a test; anything else is "configured" or "prompt guidance".

**Change process.**

6. **Everything lands by pull request** into `hunt-bots`. There is no hosted CI (GitHub Actions is off to keep the project free to run). Before opening or updating a PR, run `python scripts/hunt_bots_check.py` and paste its summary line into the PR. Every PR gets a deep-mode review (see [Review](#review)); no paid review service is used. Code owners approve `framework/`, `.github/`, `scripts/hunt_bots_check.py`, `.deep-mode.json`, and this file, except on a maintainer's own PR, where a passing deep-mode panel replaces that approval (see [Landing](#landing)).
7. **Tests with behavior.** A behavior change ships with a test that fails before and passes after, plus the docs it affects. Do not weaken a guard, cap, or test to make a check pass.
8. **The public file list is explicit.** Every tracked file under `framework/` is listed in [framework/TRACKED-FILES.txt](framework/TRACKED-FILES.txt); `scripts/hunt_bots_check.py` fails on anything else. Add new files there in the same PR.
9. **Third-party code needs its license.** Copying code (for example from the MIT omp browser tool or Orca, or the Apache-2.0 Playwright/agent-browser code) requires keeping the original notice, adding an entry to `THIRD-PARTY-NOTICES.md`, and marking modified files. Code with an unknown or incompatible license is not accepted.
10. **Upstream stays syncable.** Keep fork changes small and isolated, prefer plugins and `framework/` over core edits, and label PRs that touch upstream files with `upstream-touch`.

The gateway has run since 2026-11-08 from the checkout `runtime/hermes/source` and the venv `runtime/hermes/venv`. Hunts launch the lab install named by `LAB_HERMES_EXE` (or `--hermes` for `framework/bot.py lab`): `runtime/lab-home/installs/65793093de506825/environments/065b5c55ef0642c489baf9dda1788c7b`, whose `venv\Scripts\hermes.exe` that variable points at. Name the install by its path, because the lab home holds three others and they differ. `6e692d024accf75f` (written 2026-11-11 16:08), for one, maps 2,395 files with a different hash, and 30 of the 77 distributions it shares with the named install have other versions. On 2026-11-11 the gateway and the named install ran the same Hermes code. Every `.py` file in the install's `workspace` (2,628, of which 2,544 are under the 94 packages and modules that its editable install maps) was byte-identical to the same file in the gateway's checkout. The checkout also holds tests, evals and scripts that the install lacks. Both venvs use CPython 3.14.9. The gateway venv's 79 distributions shared with the install's venv have identical versions, and it adds 20 more: dev tools (`pytest`, `ruff`, `ty`, `debugpy`) and the MCP stack (`mcp`, `httpx2`, `sse-starlette`, `jsonschema`). The two copies update separately, so after a Hermes update recheck both from the `runtime` folder. Both commands only read the copies, through any Python 3.10 or later, never through a lab venv or Hermes. The first prints the mapped package count, the file count and a hash of the mapped code. The second writes each venv's distribution list to `%TEMP%`, ready for `Compare-Object`.

Separately, every lab command and hunt must use that install's `hermes.exe`, never the `hermes` on PATH, which self-updates against the lab home. Until 2026-11-10 22:04 every hunt used the `hunt-lab` plugin that the gateway loaded on 2026-11-08: all eight older tools for every profile, no `packet_fields`, older field lists. `framework/lab.py install` now tells the serving gateway to reload each profile's plugins (`test_hunt_lab_install.py`). - **Lab browser calls are not on the tool cam yet.** `lab_browser` (Threat Hunter and Network Analyst) drives a real browser on Arkime and the lab console with accessibility-tree refs, actionability checks and human-like input, inside a lab-origin allowlist and Arkime case scoping enforced in the browser (see [framework/README.md](framework/README.md)). Its Arkime requests bypass the guest service, so they are in each bot's `audit.jsonl`, not in `/activity`, and the tool cam does not follow them. A bot's browser closes when its process exits. Hermes's stock browser has only a blocklist and stays off for the bots.
- **The Hunt Command desktop build is not packaged as an installer yet.** `HERMES_DESKTOP_VARIANT=hunt` (`npm run pack:hunt` in `apps/desktop`, see `apps/desktop/BUILDING.md`) builds Hermes Desktop as Hunt Command: its own name, app ID and userData, the mono mark as icon (`variants/hunt/`), the Hunting Lab, Hunt Board and Cybersecurity workspace plugins bundled from `framework/` and on by default, the Hunt Command theme in dark mode for a profile with no pick, and a first-run agent install fetched and cloned from this fork. That agent checkout (`HERMES_HOME/hermes-agent`) is shared with stock Hermes on the same machine: whichever app installs it first decides its source, so after a Hunt Command first install stock Hermes runs the fork and `hermes update` follows it. The packaged app was launched on a throwaway home and every page checked (2026-11-11). Not yet done: an installer (`dist:hunt` was never run) and any update path (no feed and no in-app updater; update by pulling and rerunning `pack:hunt`), its own `hermes://` protocol (it registers the stock one, which the backend and connector flows also emit, so with stock Hermes installed too the app launched last answers `hermes://` links; start Hunt Command with `HERMES_DESKTOP_SKIP_PROTOCOL_REGISTRATION=1` to leave stock Hermes as the handler), and the upstream usage-stats prompt still names Nous.
- **Arkime sessions cannot be scored.** Generated answer keys now list, per evidence group, the `packet_fields` frames of that group's network events (cited as `frame-<n>`, tshark's `frame.number`) and the `intel_lookup` record IDs (`ioc-NNNNN`, now returned by the tool) of the fact's domains and IPs those sessions carry, and `hunt_lab.scenario score` credits either like an event ID. An intel ID is listed only in the first group of a fact that carries it, so a lookup alone satisfies at most one group. Arkime session results still carry no ID shared with the key, so a session-only claim counts only if it also cites the session's frames or events. Keys generated before this change list no alternatives and score on event IDs alone. The `packet_fields` and `intel_lookup` tool descriptions, the network and evidence stage prompts, and the Network Analyst and Threat Hunter SOULs teach the citation forms; no live hunt has used them yet.
- **Answer keys are narrow.** Most evidence groups of a generated attack fact accept one or two specific events, so a report that proves the same step through a neighbouring event is not credited. Keys have not been checked by a human.
- **Anthropic's cyber safeguards refuse some steps.** Live (2026-11-09 to 2026-11-11, about 3 refusals in about 2,150 model calls across about 25 hunts): a step's model call was declined with `finish_reason=content_filter`, category `cyber` (the coordinator's `merge` and `incident` with `claude-opus-5-5`, a follow-up with `claude-sonnet-5`); the account's `cyber_verification` is inactive. Hermes then exits 1 with zero tokens and the step ends `native_nonzero`: an optional step is dropped (a dropped `merge` now passes its follow-ups' reviewed claims to the later steps, in hunts started after patch `dropped-merge-follow-ups-v1`), and a required step halts the hunt (seen once: `incident`, 2026-11-11 02:35). The step's `diagnostic` names the refusal (`model declined to respond (finish_reason=content_filter, category cyber)`), which the worker reads from the profile's `logs/agent.log` for the step's session (see [framework/hermes_temporal/README.md](framework/hermes_temporal/README.md)); runs before 2026-11-11 recorded only the zero-token exit. The remedy is the account's enrolment in Anthropic's Cyber Verification Program, an operator action. Defense Access was issued on 2026-11-11; the next hunt (`real-win-002`, the case that had halted) completed with no refusal in 124 model calls, one hunt so far; the bots must not be reworded, or switched to another model, to evade the classifier.
- **Who decided a gate is stated, not authenticated.** The workflow records each gate decision with its sender (`decided_by`, `via` `cli`, `slack` or `automated`, and the Slack user ID) and `status` returns it (patch `gate-decider-v1`; the CLI's `--decided-by`, the gate driver and the Slack bridge send it). Like the decision note, it is what the sender states: the workflow does not authenticate the caller, and a decision sent without `--decided-by` is recorded without a name. `runtime/practice/operator-decisions/decisions.jsonl` stays an append-only operator log; when one of the operator's gates moves on, the gate driver appends the decision the workflow recorded if the log lacks it (labelled `stated: <name>`, channel `workflow_record`), so a Slack bridge line for a signal the workflow ignored is followed by the right one, not rewritten. A workflow whose first gate decision was taken before the patch lists no decisions at all, and the driver then falls back to its earlier rule.

## Contributing

The workflow is [deep-mode](https://github.com/TimothyVang/deep-mode) (MIT, adapted from Lauren Tan's [pstack](https://github.com/cursor/plugins/tree/main/pstack)): small verified units, proof from the real app, honest PR briefings, and a PR review that runs on your own agent. Install it once per machine:

- OMP: `omp plugin marketplace add TimothyVang/deep-mode`, then `omp plugin install deep-mode@deep-mode`.
- Claude Code: `/plugin marketplace add TimothyVang/deep-mode`, then `/plugin install deep-mode@deep-mode`.

Start any task with `/deep-mode:poteto <task>`. The project skill **`hunt-bots-pr`** (`.agents/skills/hunt-bots-pr/SKILL.md`) adds this repository's steps below. Agents that read `.agents/skills/` (OMP, Codex and others) find it automatically; in Claude Code or Cursor, point the agent at that file.

0. New here? Follow [GETTING-STARTED.md](GETTING-STARTED.md) first: clone, check, generate a case, install the bots, run a hunt.
1. Branch from `hunt-bots` and open the PR against `hunt-bots`. Prefer several narrow PRs to one large one; stack dependent PRs on their parent branch. Open PRs ready, not as drafts.
2. Title in Conventional Commits form, `type(scope): subject`, for example `fix(hunt_lab): report field_not_allowed refusals`.
3. Prove it works on the real thing (the lab, the desktop app, a live hunt), not only with tests. A bug fix shows the failure before and the pass after.
4. Run `python scripts/hunt_bots_check.py` (policy gate, framework tests, gitleaks when installed).
5. Write the PR body with these sections, short sentences, and nothing invented: `## Why`, `## What changed`, `## Scope` (what it leaves out), `## Tradeoffs` (only if there was a real choice), `## Blast Radius`, `## Verification` (each real run and its outcome, plus the check summary line).
6. Review with deep-mode (below). Triage every finding on its merits: fix it, dismiss it with a concrete reason, or ask. Do not churn code for nitpicks.
7. Maintainers land their own PRs with no human step: `/deep-mode:land-pr <number>` (see Landing below). A contributor's PR still needs a code owner's approval.

## Review

Reviews run on the contributor's or maintainer's own agent, through deep-mode's PR review (`skill://deep-mode/references/techniques/pr-review.md`). Its reviewers read this file and `framework/AGENTS.md` as the project constraints.

- **Before opening a PR,** self-review the branch in local mode and fix, dismiss with a reason, or ask for each finding. Put the review line (`review: ready at <short sha>, ...`) in the PR's `## Verification`.
- **Maintainers** review an open PR with `/deep-mode:review-pr <number>`. It keeps only findings a code read or a run proves and posts one comment-only review (it asks first on a repository that isn't yours); a new push gets a re-review.
- **Optional second opinion:** deep-mode's pr-agent technique runs PR-Agent (`describe`, `review`, `improve`) through `omp -p` on whatever subscription your omp is logged into, Claude or Codex, and posts to your PR; triage its findings like any other. It draws on that subscription's usage limits; no API key or paid service.
- deep-mode's security-audit gate is not enabled here: it needs GitHub Actions, which this project keeps off.
- A clean review never replaces the gate or the proof on the real app.

Reviewers flag these as blocking, in addition to the rules above:

- `framework/hunt_lab/**`: bot lab tools stay read-only, scoped to the loaded case, and reach only the guest lab service, or a connected case's host-side connected service, on `127.0.0.1`, through `hunt_lab/endpoints.py`; no VM control, live capture, other hosts, or answer-key access. Refusals relay only fixed snake_case error codes to the bot, never backend free text, and host-advertised field lists stay equal to the guest allowlists (`test_hunt_lab_tools.py`, `test_lab_server.py`).
- `framework/hermes_temporal/**`: a workflow behavior change is gated by a new `workflow.patched()` ID so recorded histories replay unchanged; the workflow keeps its execute and review gates, the operator's two decisions (scope approval and the final report) stay human, and any automated gate approval is recorded as automated; no new retries without explicit approval.
- `framework/**`: operator-only material (answer keys, `truth.json`, scoring rubrics) is never reachable from bot prompts, tools or the guest payload. Every tracked file is in `framework/TRACKED-FILES.txt`, and shipped files are also in the portable package lists (`package_portable.py` `FILES` and `test_package_portable.py` `APPROVED_FILES`).
- `framework/**`, `tools/browser*`, `apps/desktop/**`: browser automation enforces the lab-origin allowlist inside the browser (navigations, frames, new tabs), not only by scanning code for URLs.

## Landing

A maintainer's own PR lands without a human. Running `/deep-mode:land-pr <number>` is the maintainer's authorization; [`.deep-mode.json`](.deep-mode.json) (`"autonomousMerge": true`) records the repo's standing opt-in, and setting it to `false` makes `land-pr` stop before the merge and ask. These are deep-mode's development agents, not the hunt bots, and they post only on the PR. `land-pr` runs deep-mode's pr-conversation technique: reviewer bots post their findings in the PR, the author bot answers each one with a fix or a reason, three verifier bots vote on the final head, and on a pass the author bot merges with `gh pr merge --squash --admin --match-head-commit <sha>`. The panel replaces the code-owner approval the branch requires. `hunt-bots` has no required status checks (GitHub Actions is off), so the gate stands in for them: pr-conversation runs the repo's local gate at the merge SHA, here `python scripts/hunt_bots_check.py`, merges only on `-> PASS`, and quotes that line in its merge note. This repository has more than one writer, so deep-mode also checks every commit: one the landing session made itself passes, and any other must be the maintainer's own and signed with a verified signature; otherwise the PR waits for a human. Every bot runs on the maintainer's own omp subscription. Contributor PRs and PRs from forks are excluded.
