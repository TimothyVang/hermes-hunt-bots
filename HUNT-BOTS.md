# Hermes Hunt Bots

A fork of [NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent) that turns the Hermes desktop app into a six-bot threat-hunting team. Each bot drives its own read-only lab tool (Elastic, Arkime, redacted packet fields from the case's saved capture, a threat-intel feed, a detection tester) against invented data in a local QEMU lab VM, and hands its findings to the next bot through validated, human-gated handoffs.

Built in the open. This file is the project's rulebook: **every contributor, human or AI agent, follows it, and it overrides upstream guidance where they conflict.**

## Rules (enforced)

**Safety.** These are not negotiable and Greptile reviews every PR against them.

1. **Synthetic data only.** Never commit real logs, packet captures, customer data, credentials, tokens, cookies, session stores, or anything marked CUI/NSS. Generated cases and answer keys stay in `runtime/`, next to the clone.
2. **Tools stay read-only and lab-local.** Bot tools may only read the loaded case through the guest lab service on `127.0.0.1`. No tool may control the VM, capture live traffic, reach other hosts, or read an answer key. `packet_fields` reads only the case's saved capture (`tshark -r` on `evidence/traffic.pcap`), never live traffic, and returns only allowlisted, redacted fields (ADR 0003 in the planning notes); the guest's argument list, field allowlist, filter grammar and URI redaction are enforced and tested with a faked tshark (`framework/test_lab_server.py`). One live run (2026-11-10, generated case `team-med-011`, tshark 3.6 in the guest) returned DNS, TLS and HTTP fields, refused denied fields and filters, answered `field_unavailable` for JA4, and returned every query string among the first 200 HTTP requests as `?[redacted]`. Browser automation may only open lab origins (`127.0.0.1` / `localhost` lab ports); a change that lets a bot browse elsewhere is rejected.
3. **The operator makes two decisions per hunt.** Following the project's accepted decision record on two human decisions per hunt (ADR 0002 in the planning notes, outside this repository), the operator approves the scope before any hunter queries data, and accepts or rejects the final report. The gates between them may be approved automatically; every automated approval is recorded as automated and never presented as human. Response actions remain human decisions. Never fabricate approvals, evidence, model output, scores, or test results. Simulated or scripted runs are labelled as such.
4. **No real-money trading** and no unattended external actions (messaging, schedules, posting) without explicit opt-in. The bots have no messaging tools. The operator's Slack bridge (`operator/slack_gates.py`, ADR 0004 in the planning notes) is opt-in: it is off unless the operator starts it with their own Slack tokens, and it carries only the operator's own two decisions. Its cards carry bot-written summaries only for synthetic lab cases; real or work data gets ID-and-status cards.
5. **Honest claims.** Docs and PR descriptions state what was actually run and observed. "Enforced" means enforced at runtime, with a test; anything else is "configured" or "prompt guidance".

**Change process.**

6. **Everything lands by pull request** into `hunt-bots`. There is no hosted CI (GitHub Actions is off to keep the project free to run). Before opening or updating a PR, run `python scripts/hunt_bots_check.py` and paste its summary line into the PR. Greptile reviews every PR. Code owners approve `framework/`, `.github/`, `scripts/hunt_bots_check.py`, and this file.
7. **Tests with behavior.** A behavior change ships with a test that fails before and passes after, plus the docs it affects. Do not weaken a guard, cap, or test to make a check pass.
8. **The public file list is explicit.** Every tracked file under `framework/` is listed in [framework/TRACKED-FILES.txt](framework/TRACKED-FILES.txt); `scripts/hunt_bots_check.py` fails on anything else. Add new files there in the same PR.
9. **Third-party code needs its license.** Copying code (for example from the MIT omp browser tool or Orca, or the Apache-2.0 Playwright/agent-browser code) requires keeping the original notice, adding an entry to `THIRD-PARTY-NOTICES.md`, and marking modified files. Code with an unknown or incompatible license is not accepted.
10. **Upstream stays syncable.** Keep fork changes small and isolated, prefer plugins and `framework/` over core edits, and label PRs that touch upstream files with `upstream-touch`.

## Known gaps (help wanted)

- **Delegated children's core tools are not verified.** Plugin tools and delegation targets are enforced at runtime. The `hunt_lab` plugin registers only the tools each profile owns (`TOOL_OWNERSHIP` in `framework/hunt_lab/query_adapter.py`, the same map `native_team.py` writes as `agent.allowed_tool_names`), so Hermes's existing unknown-tool check refuses any other plugin tool before it runs; the Incident Response Lead and unknown profiles register none (`framework/test_hunt_lab_tools.py`, `RegistrationTests`). Checked live on the installed Hermes (2026-11-10): the tool definitions it hands each profile's model were `framework-builder` → `detection_test`, `elastic_aggregate`; `framework-coordinator` → none. The coordinator's delegation targets are the `delegation.backends.profile_routes.profiles` list, which Hermes 0.23.0 turns into the `task.profile` enum and enforces before the plugin runs; a task with no profile runs as `framework-researcher` (`profile_routes.default`). Core tools are limited by the `platform_toolsets.cli` and `agent.disabled_toolsets` values that `native_team.py apply` writes; whether a delegated child gets its own profile's core toolsets rather than the coordinator's is not verified without `framework/desktop/native-role-policy.diff` ported to 0.23.0.
- **Lab browser calls are not on the tool cam yet.** `lab_browser` (Threat Hunter and Network Analyst) drives a real browser on Arkime and the lab console with accessibility-tree refs, actionability checks and human-like input, inside a lab-origin allowlist and Arkime case scoping enforced in the browser (see [framework/README.md](framework/README.md)). Its Arkime requests bypass the guest service, so they are in each bot's `audit.jsonl`, not in `/activity`, and the tool cam does not follow them. A bot's browser closes when its process exits. Hermes's stock browser has only a blocklist and stays off for the bots.
- **Desktop rebrand** (`apps/desktop/product-identity.cjs`) and shipping the Hunting Lab page as a bundled desktop plugin.
- **Arkime sessions cannot be scored.** Generated answer keys now list, per evidence group, the `packet_fields` frames of that group's network events (cited as `frame-<n>`, tshark's `frame.number`) and the `intel_lookup` record IDs (`ioc-NNNNN`, now returned by the tool) of the fact's domains and IPs those sessions carry, and `hunt_lab.scenario score` credits either like an event ID. An intel ID is listed only in the first group of a fact that carries it, so a lookup alone satisfies at most one group. Arkime session results still carry no ID shared with the key, so a session-only claim counts only if it also cites the session's frames or events. Keys generated before this change list no alternatives and score on event IDs alone. The `packet_fields` and `intel_lookup` tool descriptions, the network and evidence stage prompts, and the Network Analyst and Threat Hunter SOULs teach the citation forms; no live hunt has used them yet.
- **Answer keys are narrow.** Most evidence groups of a generated attack fact accept one or two specific events, so a report that proves the same step through a neighbouring event is not credited. Keys have not been checked by a human.
- **Filming tools assume a serial hunt.** `operator/film/` and `operator/toolcam/` expect nine stages that start one at a time and do not know the `dropped` step state of a parallel hunt.
- **Anthropic's cyber safeguards refuse some steps.** Live (2026-11-09 and 2026-11-10, a few steps across dozens of hunts): a step's model call was declined with `finish_reason=content_filter`, category `cyber` (seen on the coordinator's `merge` with `claude-opus-5-5` and on a follow-up with `claude-sonnet-5`); the account's `cyber_verification` is inactive. Hermes then exits 1 with zero tokens, the step ends `native_nonzero` and is dropped, and a dropped `merge` loses the follow-ups' work. The step's `diagnostic` (exit code and a redacted stderr line, see [framework/hermes_temporal/README.md](framework/hermes_temporal/README.md)) shows the zero-token exit but not the refusal; the refusal is in the profile's `logs/agent.log`. The remedy is the account's enrolment in Anthropic's Cyber Verification Program, an operator action; the bots must not be reworded to evade the classifier. The Hunt Board shows only the reason code, and the receipt store does not keep the diagnostic.
- **Who decided a gate is recorded beside the workflow, not in it.** The decision signal carries no identity, so the operator's name and Slack user ID live in the decision note and in `runtime/practice/operator-decisions/decisions.jsonl`. The Slack bridge logs a decision once its signal is sent while `status` showed the gate open; a decision sent through another channel in that moment could make its line wrong. The gate driver's log says so when the workflow then shows a different outcome, but the decision log is not corrected.

## Contributing

The workflow follows [pstack](https://github.com/cursor/plugins/tree/main/pstack)'s poteto-mode playbooks: small verified units, proof from the real app, honest PR briefings. pstack is vendored in `.agents/` (MIT), and the project skill **`hunt-bots-pr`** (`.agents/skills/hunt-bots-pr/SKILL.md`) walks you or your coding agent through every step below. Agents that read `.agents/skills/` (OMP, Codex and others) find it automatically; in Claude Code or Cursor, point the agent at that file.

0. New here? Follow [GETTING-STARTED.md](GETTING-STARTED.md) first: clone, check, generate a case, install the bots, run a hunt.
1. Branch from `hunt-bots` and open the PR against `hunt-bots`. Prefer several narrow PRs to one large one; stack dependent PRs on their parent branch. Open PRs ready, not as drafts.
2. Title in Conventional Commits form, `type(scope): subject`, for example `fix(hunt_lab): report field_not_allowed refusals`.
3. Prove it works on the real thing (the lab, the desktop app, a live hunt), not only with tests. A bug fix shows the failure before and the pass after.
4. Run `python scripts/hunt_bots_check.py` (policy gate, framework tests, gitleaks when installed).
5. Write the PR body with these sections, short sentences, and nothing invented: `## Why`, `## What changed`, `## Scope` (what it leaves out), `## Tradeoffs` (only if there was a real choice), `## Blast Radius`, `## Verification` (each real run and its outcome, plus the check summary line).
6. Greptile reviews automatically. Triage every comment on its merits: fix it, dismiss it with a concrete reason, or ask. Do not churn code for nitpicks.
